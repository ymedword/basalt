# Basalt Constitution

Basalt 是用 Go 实现的面向企业场景的 Agent OS：自托管单 Go 二进制，作为统一底座运行多个业务 Agent，共享渠道接入、模型路由、工具调用、记忆系统与沙箱执行。工作区及持久化数据由企业自托管；接入外部模型或工具时，相应请求数据按配置发送到服务端。

本宪法规定十条不可违背的核心原则与五条架构约束；每条都带「违反时的症状」与「复核方式（可验证）」，可在代码与命令层面判卷。所有实现（人类或 AI）动工前**必须**逐条对照。

## Core Principles

### I. 自实现 ReAct 循环

**Basalt 主程序不得将 Agent 框架作为直接或间接依赖引入。** 允许使用协议 SDK（如 MCP SDK），但 SDK 不得接管 ReAct 循环或自动执行工具。核心循环由本仓库代码实现（`ReActLoop`）。

- **违反时的症状**：框架接管循环，工具被调两次，或行为不可控、不可复现
- **复核方式（可验证）**：`go.mod` 不出现框架坐标（eino / langchaingo / adk-go / trpc-agent-go 等）；`ReActLoop` 循环体为仓库内代码
- **理由**：完全可控、可审计、可定制；框架会接管循环并引入版本与行为耦合

### II. LLM 客户端只做协议调用

**不得**启用 LLM 客户端的任何自动工具循环能力；调用面只到 Chat 请求 / 响应结构（含工具 schema 序列化）。工具调度的唯一归属是 `ToolExecutor`。结果回填与历史写入的责任分界：**ReActLoop 组织轮次，并在正常运行中统一追加模型响应与工具结果；ToolExecutor 执行工具、记录审计并返回结构化结果（不写历史）；用户输入由 `AgentService` 写入；崩溃 / 取消后的半截工具组由恢复路径补齐。上述入口必须复用同一消息仓储（`core` 定义的消息写入接口），不得出现第二套追加路径，不得重复追加同一消息。**

- **违反时的症状**：工具被客户端与执行器各调一次；或同一消息被两处重复追加；或半截工具组无人补齐（会话从此哑掉）
- **复核方式（可验证）**：调用面只有 Chat 请求 / 响应结构；装配处无 agent / runner 类 API；消息写入点收敛在一条仓储通道上——正常运行追加只发生在 `ReActLoop`、用户输入只发生在 `AgentService`、恢复只补半截工具组（清点消息写入接口的调用点，无第四处；`ToolExecutor` 不写历史）
- **理由**：工具被调两次是全项目最容易踩的坑；写入入口少而明确（一条仓储通道 + 三种各司其职的入口）才能既避免重复追加、又让崩溃恢复有唯一补写点

### III. Provider 必须显式映射

`provider name → 客户端实例` 的映射表**必须**由装配层在受控发布时显式构建。新 Run 在准入时取得当前已发布映射；该 Run 后续路由始终只查准入时固定的映射。**不得**遍历推断、**不得**"取第一个"，**不得**在运行中原地修改映射表。

每次受控发布**必须**先构建一份不可变的新映射并完成校验；校验通过后原子替换当前发布指针。发布成功后，新准入的 Run 取得新映射；已开始的 Run 继续持有其准入时固定的旧映射。发布失败**必须**保留旧映射并保持旧 Run 可用。旧映射及其连接／句柄只能在“不再是当前发布版本、且最后一个引用它的 Run 与在途调用均已释放”后回收；当前发布版本即使暂无 Run，也**不得**回收。

- **违反时的症状**：多 Provider 时路由错乱；Go map 遍历顺序**随机**，行为不可复现；发布失败切断在跑 Run 的连接；旧连接在仍有调用时被关闭；新发布切换后旧 Run 被错误改查新映射
- **复核方式（可验证）**：装配／发布处无 `range` 选择逻辑；新 Run 准入取当前发布映射，Run 内路由只查准入时固定的映射；映射对象带版本且不可变；发布失败用例保留旧映射；发布切换后旧 Run 仍只查旧映射；旧映射回收用例在最后一个 Run／调用释放前拒绝关闭；当前发布版本零 Run 时不被回收
- **理由**：多 Provider 并存时类型相同，扫描推断必然歧义；在线发布还要求“新 Run 用新版本、旧 Run 固定旧版本、失败不破坏在跑工作”，否则可审计与可用性不能同时成立

### IV. 一个目录 = 一个 Agent；技能声明式绑定 + 渐进披露

`AGENT.md` frontmatter 即运行配置（含 `skills:` 声明），正文为任务指令。**一个目录 = 一个 Agent**。技能绑定**必须**由 frontmatter 的 `skills:` 列表声明（元素 = 公共技能库目录名，声明即绑定，各平台一致）；**不得**引入软连接 / 本地目录类绑定机制。技能按 L1（name + description + 技能库路径）→ L2（`read_file` 读 `SKILL.md` 正文）→ L3（附属资源按需再取）渐进披露；**不得**预载正文、**不得**新增 `use_skill` 工具。声明名在技能库中无实体 → **该 Agent 整只不注册**（WARN 点名）。

- **违反时的症状**：Agent 目录被当 Tool 注册，执行时报错；或技能卡片不出现而其它一切正常
- **复核方式（可验证）**：加载器有 `AGENT.md` 专项测试；`skills:` 缺实体 → 该 Agent 不注册
- **理由**：业务方零代码上线；杜绝平台差异（软连接类绑定机制在 Windows 不可行）

### V. 审计 day-one 且 fail-closed

既有审计表在 US-1 随 schema 建齐；写入自对应 US 起——`runs` 自 US-4（首次运行）、`llm_calls` 自 US-2（首次 LLM 调用）、`tool_invocations` 自 US-4（首次工具执行）。**管理面高权限变更的审计表／字段随对应功能引入时建齐，不追溯声称 US-1 已建这些表。** **模型调用、工具执行与管理面高权限变更均必须先写入 pending 审计记录；预写失败不得发出对应调用或执行对应变更。模型调用与工具执行的终态、写入失败与崩溃恢复遵循运行时契约 §7.2；管理面变更按独立操作契约查证实际结果、恢复或补偿，不套用模型／工具调用恢复规则，也不得盲目重做。管理面变更使用独立操作标识，不混写为模型／工具调用。** **不得**以"日志够了"为由跳过落库。

- **违反时的症状**：扩展阶段审计无从落地；或"跑都跑了却没记录"；或管理面高权限变更预写失败仍执行；或管理变更盲目重做造成重复写入
- **复核方式（可验证）**：任一 Demo 跑完查 SQL 有记录；模型／工具审计预写失败时调用**不得**发出；管理变更预写失败时**不得**执行；管理操作有独立操作标识，未混写为模型／工具调用；管理变更恢复按独立操作契约查证实际结果后再决定恢复或补偿
- **理由**：可审计是差异化能力，不是扩展阶段功能；模型／工具与调用恢复按运行时契约 §7.2；管理面写入配置同样必须"先记后做"，且管理变更的恢复不能套用调用恢复或盲目重做

### VI. 授权与执行分离（两接口）

**授权与受控命令执行分别通过 `Policy` 与 `CommandRunner` 接口完成；调用方不得直接依赖 `WhitelistPolicy`、`LocalRunner` 等具体实现。核心阶段由装配层显式选择这两个实现。** 签名以技术方案 §4.3 为准：`Policy.Check(ctx, action) error`；`CommandRunner.Run(ctx, cmd) (CommandResult, error)`。`CommandRunner` 负责 cwd、环境变量、输出上限、取消与进程树清理。升级（容器 / microVM）= 两接口各新增实现 + 装配切换，调用方零改动。**不得**把本条读成"所有工具都必须经过 `CommandRunner`"——它只承担受控命令执行（`SHELL_COMMAND`）；文件 / HTTP / 通知等动作经 `Policy` 授权后在各自执行路径落地。

- **违反时的症状**：升级要改多处；授权与执行职责糊在一起，无法单独替换
- **复核方式（可验证）**：调用方代码 grep 不到 `WhitelistPolicy` / `LocalRunner`（只在装配处与实现文件出现）；装配处显式选择实现；容器档 = 两接口各加实现 + 装配切换
- **理由**：升级承诺是"两个接口各新增实现 + 装配切换，调用方零改动"；"单接口不变"的旧承诺已作废

### VII. 同步执行 + context 只承载取消 / 截止 / 追踪

全程同步阻塞，goroutine-per-request；**不得**引入异步编排。`context.Context` **只承载取消、截止时间与追踪标识**；**逐处审查业务代码中的 `context.WithValue` 使用，只允许追踪标识；Profile、Session、RunEnv、ToolEnv 等业务状态必须显式传递。** **不得**用包级变量模拟 ThreadLocal。

- **违反时的症状**：隐式耦合、取消失效、并发串号（Go 无 ThreadLocal，塞进 context 等于把隐式依赖合法化）
- **复核方式（可验证）**：逐处审查业务代码中的 `context.WithValue`——只允许追踪标识；业务状态一律走显式类型化参数；grep 无包级可变状态存 Profile / Session；请求路径无自建 worker pool
- **理由**：Go 无 ThreadLocal，"显式传递"的载体是类型化参数而不是 context

### VIII. 单二进制纪律

**发布产物必须使用 CGO_ENABLED=0 构建，运行时代码和管理台静态资源随单 Go 二进制交付。核心底座无需外部数据库、缓存或消息队列；模型服务、显式配置的 MCP Server 及其运行环境属于按配置接入的业务能力，依赖条件应单独说明。竞态测试与发布构建分开执行；测试 job 可按 -race 要求启用 CGO。** 依赖最小化：**本表（架构约束 · 技术栈）与已批准计划（spec / plan / 模块执行颗粒度文档）内的依赖可直接落地**；表外的**新增第三方坐标或版本变更**先经用户确认。

- **违反时的症状**：交叉编译失败 / 目标机缺动态库；或 `-race` 与 `CGO_ENABLED=0` 互相打架
- **复核方式（可验证）**：`CGO_ENABLED=0 go build` 通过；发布产物按**各目标平台**分别验证——Linux 用 `ldd` / `file` 断言静态，macOS / Windows 验证无额外依赖即可启动；`-race` 只在测试命令 / job 中启用
- **理由**：交付形态是本项目的核心卖点；破例即是产品破位

### IX. 不用 ORM，手写 SQL

**不得引入 ORM，不得由 ORM 自动推断或修改数据库结构。允许启动时按 `schema_version` 执行已审查、版本化的显式 SQL 迁移；已发布迁移不得改写，只允许追加。** 建表用 schema 幂等脚本；repository 接口定义在 `core`、实现在 `storage`。

- **违反时的症状**：SQLite 迁移能力弱，ORM 自动迁移反复出坑；SQL 不可审计、不可优化
- **复核方式（可验证）**：`go.mod` 无 ORM 坐标；建表与迁移只在显式 SQL 脚本与 `schema_version` 记录里——复核**必须**覆盖建表脚本**与升级迁移脚本**，并逐版审查 `schema_version` 记录
- **理由**：显式 SQL 可审计、可优化；"只追加不改写"保证已发布版本的升级路径可推演

### X. 五大能力优先，范围卡紧

核心阶段范围**以需求文档 §7.1 与已批准的 US 清单（台账 `docs/us/REGISTRY.md`）为准**——运行时内核五大能力（Provider / ReAct 循环 / Memory / Tool 体系 / Web Service）之外，管理台与观测、Agent 动态管理、每日 Demo、发布收尾等**已登记在 US 清单内的交付物同样属于核心阶段**。**核心阶段的管理台必须提供最小管理面认证：非回环管理访问必须要求 admin token；回环可以显式采用本机信任。非回环管理部署未配置有效 admin token 时拒绝启动；token 模式下管理请求未提供或提供无效凭据时拒绝访问。回环本机信任模式不要求 token，但仅适用于直接回环连接；反向代理／转发不得因上游连接来自回环而绕过认证。该认证只保护管理面，不得被表述为企业身份体系。** **企业级治理层（调用方 API Key／QPS／配额、企业身份／SSO／RBAC／多租户、审计查询、Tool Policy）仍放扩展阶段。** 完不成的功能挪到扩展阶段，**不得**砍验收。

- **违反时的症状**：功能蔓延，内核迟迟不完整；或反向误判——把已批准 US 清单里的交付物当成"超出五大能力"而拒做；或把最小 admin token 宣称为企业认证／SSO／多租户已完成；或反向代理因上游连接是回环而绕过认证
- **复核方式（可验证）**：每 US 范围对照需求文档 §7.1 边界**与台账已登记行**；清单外功能一律进扩展阶段（Roadmap 或新增 US，先经用户裁决）；非回环管理部署未配置有效 admin token 时拒绝启动；token 模式下管理请求无凭据或凭据无效时拒绝访问；回环本机信任仅限直接回环连接，反向代理／隧道用例不能凭上游回环地址绕过认证；管理 token 不能替代调用方 Key，调用方 Key 也不能获得管理权；检查文档与页面未把最小认证写成企业身份／SSO／多租户已完成；**不得**以"超出五大能力"为由判已批准的 US 交付物越界
- **理由**：先交付最小完整内核，企业级治理在真实使用数据验证后再做；管理台会写入配置，远程访问若没有最小保护会把管理面直接暴露，因此"管理面最小认证"与"企业级治理"必须分开

**Go 版本语义**（Go 1.21 起，[官方工具链文档](https://go.dev/doc/toolchain)、[go 指令语义](https://go.dev/ref/mod#go-mod-file-go)）：`go` 行声明的是**最低版本要求**——低于它的工具链会被拒绝，**它不是准确版本锁定**；准确构建版本由 **`toolchain` 指令**（`toolchain go1.27.2`）与 **CI 工具链配置**（`actions/setup-go` 的 `go-version: 1.27.2`）共同表达。本地工具链低于 `toolchain` 行时按 `GOTOOLCHAIN=auto` 切换 / 下载，高于它则照用。**不得**把 1.27.2 表述为"`go.mod` 锁定"。

### 依赖方向与包结构纪律

- 依赖方向无环：`channel` / `web` / `cli` → `core` ← `provider` / `memory` / `tool` / `storage` / `workspace`；`app` 是唯一装配层
- `core` 只依赖标准库与内部接口；接口**必须**定义在消费方
- cron 等第三方库的适配**必须**放在独立内部包；`core` 保留接口与纯业务逻辑，由 `app` 完成装配
- 同类语义**不得**出现第二套实现（解析 / 注册 / 审计写入路径唯一）

### 凭证与资源绑定纪律（2026-10-23 修订；替代原「凭证纪律」三条）

1. **两种凭据模式**：凭据只允许 `${ENV_VAR}` 环境变量或管理台托管密文两种模式；明文**不得**出现在定义文件、`AGENT.md`、资源版本、提示词、日志、审计、诊断导出或浏览器持久存储中。
    - **违反时的症状**：页面回显 Key；日志 / 审计 / 导出出现明文；托管表存明文。
    - **复核方式（可验证）**：响应 schema 无明文回显字段；日志、审计、导出与浏览器存储的泄漏扫描用例通过；托管表只存 `nonce` / `ciphertext` / `key_id` / 尾号。
2. **加密与主密钥边界**：托管密文**必须**使用 AES-256-GCM（32 字节密钥、12 字节随机 nonce、AAD 绑定目标与版本）；主密钥**必须**独立于工作区并按平台最小权限保存；**不得**写入工作区、配置文件、环境变量或日志。
    - **违反时的症状**：工作区备份直接带走主密钥；nonce 复用；GCM 标签未校验。
    - **复核方式（可验证）**：加密只经标准库 `crypto/aes` + `cipher.NewGCM`；nonce 每次随机且在 `key_id` 内不重复（测试）；主密钥路径在运维文档中位于工作区外；日志与诊断导出无密钥字节。
3. **不可变版本与目标绑定**：每条凭据**必须**有不可变版本；目标地址随版本固定并参与 AEAD 关联数据；**不得**在版本之间复用或改写绑定。
    - **违反时的症状**：更换 `base_url` / webhook 后旧密文仍可解密并发送；密文被移植到另一目标。
    - **复核方式（可验证）**：解密用 `target_binding` 重建 AAD；改挂目标 / 版本的测试解密失败；版本内容列只插入、无原地更新路径。
4. **按版本撤销**：撤销**必须**按版本状态持久化；**不得**只凭凭据身份当前是否 active 判断旧 Run 是否可用。模型在 Run 准入固定版本、调用检查点查撤销；通知每次发送解析版本并记录。
    - **违反时的症状**：撤销后旧 Run 继续成功调用；撤销一个版本误废其他版本。
    - **复核方式（可验证）**：撤销测试覆盖「旧 Run 下一检查点失败、新 Run 不可准入、其他版本不受影响」；模型 / 工具调用检查点存在撤销查询；发送记录含解析版本。
5. **托管写入审计**：托管凭据的写入**必须**先写 `pending` 管理审计，预写失败**不得**写入；读取接口只回状态与必要尾号，**不得**回明文。
    - **违反时的症状**：预写失败仍落密文；接口返回完整 Key。
    - **复核方式（可验证）**：预写失败注入测试零写入；响应无明文字段；尾号最多 4 位。
6. **启动依赖判定**：启动时**必须**从持久化声明与绑定判定当前托管模型连接（当前已发布、且被活动区已注册 Agent 绑定的 managed 模型连接；未删除的 managed 通知渠道只作单独统计，仅用于 `secrets init` 条件），再套用失败策略；仅当存在当前托管模型连接且其凭据无法安全解密时**必须**拒绝启动；纯 env 或仅通知托管实例**不得**因缺少主密钥被阻断；**不得**静默回落 env、在**已有密文**的实例上自动生成新密钥或跳过；**新建实例的首次初始化**生成主密钥不属此禁（该实例没有既有密文可失效，范围见第 14 条）。
    - **违反时的症状**：纯 env 实例因缺主密钥起不来；托管模型不可用却静默启动；在已有密文的实例上自动生成新密钥使旧密文永久不可解。
    - **复核方式（可验证）**：四种场景测试通过（全 env + 托管 webhook 正确密钥；无托管资源但密钥已初始化；无密钥且 env 工作；必需托管模型凭据不可解）；启动日志点名资源与原因，不打印明文。
7. **主密钥按需加载**：主密钥**必须**按需读取——只有首次托管写入、模型连接测试、通知测试 / 发送、后续受控发布、启动必需校验这些操作才读取；每次读取都**必须**校验路径、平台权限、格式与 `key_id` 身份；失败**必须**拒绝该操作，**不得**静默回落环境变量或跳过校验；「启动时跳过解密」**不得**解释为「运行期永不加载」。
    - **违反时的症状**：密钥权限被改宽后仍继续使用；启动未读密钥导致运行期也永不读；解析失败静默用 env。
    - **复核方式（可验证）**：解析服务为唯一读取路径；路径 / 权限 / 格式 / `key_id` 不匹配测试均拒绝；覆盖「启动不读、后续操作按需读」的场景。
8. **运行时使用范围**：资源使用范围**必须**在运行时强制——Agent 专属仅所有者可用；工作区共享可按授权使用；空白名单只放宽到有资格的资源；**不得**以同名匹配或隐式回退绕过范围。
    - **违反时的症状**：Agent A 调用 Agent B 的专属连接；空白名单暴露全部资源；同名资源被自动顶替。
    - **复核方式（可验证）**：准入、模型调用与通知发送三处均按 `RunEnv.AgentUID` 判资格；跨 Agent 专属资源测试拒绝；空白名单只返回 shared ∪ 自身 exclusive。
9. **稳定资源身份与墓碑**：资源身份**必须**由不可变 `resource_uid` 承载，名称只是标签；删除后同名重建是**新 UID、新凭据身份**，旧引用仍指向旧 UID 并显示资源已删除，**不得**按同名自动重连；UID 级身份与删除事实**必须**独立保存，**不得**因为按名指针被同名重建覆盖而丢失。
    - **违反时的症状**：同名重建后旧 Agent 悄悄用上新 Key；旧 UID 删除记录查不到；版本号跨重建被继承。
    - **复核方式（可验证）**：UID 级身份表在指针复活时仍保留旧 UID 的 deleted 行；同名重建生成新 UID 且版本从 1 起；旧引用解析为 deleted 而非新资源。
10. **绑定权威**：Agent 权威配置是资源 UID 绑定的**唯一权威**（`AGENT.md` 正式扩展字段 `resource_bindings`）；数据库绑定表是可重建投影。每个引用**必须**恰有一条绑定；**不得**在迁移、复制、恢复、启动、准入或原文保存时按同名资源自动补绑；显式重绑属于 Agent 配置变更，**必须**受 Agent 内容条件写保护；复制、归档、恢复、导出**必须**完整携带绑定；Agent **不得**保存凭据 ID 或 Key。
    - **违反时的症状**：投影表与 `AGENT.md` 漂移；重建投影后绑定丢失；复制 Agent 后按名自动改绑；重绑绕过 ETag。
    - **复核方式（可验证）**：删除并重建投影后绑定与 `AGENT.md` 一致；迁移 / 复制 / 恢复 / 导出用例携带 UID；缺绑定在准入拒绝且不自动补；重绑走 Agent 内容 ETag，412 零写入；`AGENT.md` 无凭据 ID / Key 字段。
11. **显式通知模式与受控装配**：通知意图**必须**用显式 `notify_mode` 表达（`none` / `all_eligible` / `allowlist`）；`none` 与 `all_eligible` 时渠道列表**必须**为空，`allowlist` **必须**至少一个；空数组**不得**表示「不使用通知」；禁止通知**必须**由 notify 发送授权层强制执行，**不得**只靠隐藏按钮或删除提示。生效 `tools` **必须**与通知意图一致：`notify_mode` ≠ `none` 且渠道资格校验通过时，受控写面**必须**把 `notify` 装配进生效 `tools`；`notify_mode` = `none` 时**必须**不装配 `notify`；这是系统**唯一**允许的自动增删工具，且**必须**作为可见变更随保存结果返回，**不得**静默改写。除 `notify` 外的任何工具名，系统**不得**自动增删。系统代投的 Run（任务已绑定投递目标）**不得**向模型提供 `notify`，模型只返回正文，授权层仍须兜底拒绝。
    - **违反时的症状**：页面显示「不使用通知」但模型仍能发送；空数组被解释为「不限制」；保存配置时其他工具被悄悄改动，或 `notify` 增删不告知用户；系统代投 Run 里模型反复调用被拒的 `notify`。
    - **复核方式（可验证）**：三态组合校验测试（`none` / `all_eligible` + 非空拒绝；`allowlist` + 空拒绝）；`none` 下 notify 工具返回固定错误；保存前后 `tools` 差异只允许 `notify` 一项且出现在返回的 `changes` 中；直接请求授权层在 `none` 下发送被固定拒绝；系统代投 Run 的工具清单不含 `notify`。
12. **显式凭据模式**：`credential_mode` **必须**显式——创建未声明时只按 env 规则；managed 创建**必须**显式声明；更新未声明时保持当前模式；切换**必须**显式并给出目标模式所需值；字段省略表示保留，空串**必须**拒绝，**不得**靠空值猜测保留、替换或撤销；所有入口**必须**执行 owner、目标绑定与使用范围检查。
    - **违反时的症状**：老客户端普通更新把 managed 误判成 env；空 Key 被当成删除凭据；越权修改他人连接。
    - **复核方式（可验证）**：兼容矩阵测试（创建 / 更新 / 切换 × 声明 / 省略 / 空串）；空串返回 400；owner、绑定与范围检查覆盖全部写入口。
13. **崩溃恢复四证**：文件与数据库之间的崩溃恢复**必须**以操作 ID、数据库提交事实、版本与哈希四条联立证据判定；**不得**只凭文件哈希、盲目重放、重新加密，或把「保留旧运行时 + WARN」当作恢复完成；无法证明时**必须**阻断并标 `unknown`。
    - **违反时的症状**：半写文件被当成成功；重复加密导致版本错乱；`unknown` 被当成已完成。
    - **复核方式（可验证）**：恢复矩阵测试（applied / not_applied / indeterminate）；`unknown` 阻断且不自动补做；恢复路径不重新加密。
14. **凭据操作由人执行；主密钥初始化例外**：凭据的录入、替换、撤销**必须**由人执行。**主密钥初始化可以由用户启动的安装 / 实例初始化流程自动完成**，但只限**可证明的新实例**——目标密钥文件不存在，且该实例既无托管密文、也无主密钥历史记录（含未完成初始化的残留）。存量密钥缺失、损坏或 `key_id` 身份不匹配时**必须**拒绝替换并进入恢复处置，**不得**据此生成新密钥；初始化中断后只恢复能证明来源的残留，无法证明来源时进入恢复状态而**不得**删除既有文件。运行中的 Agent 任务**不得**管理或获取主密钥，只能使用凭据；Agent 运行时**不得**创建、读取明文或修改凭据。
    - **违反时的症状**：模型经工具创建或轮换 Key；运行时日志出现明文；初始化流程在已有密文或主密钥历史的实例上生成新密钥，使旧密文永久不可解；Agent 任务取得主密钥。
    - **复核方式（可验证）**：工具清单无凭据写工具；凭据写入口只挂在管理端点并要求 admin token；运行时只取得可用句柄，不取得明文；初始化流程的新实例判定用例（目标文件已存在 / 存在托管密文 / 存在主密钥历史 / 存在无法证明来源的残留 → 拒绝生成并进入恢复），且并发初始化只有一个成功；Agent 运行时无任何读取主密钥的路径。
15. **不降低既有要求**：本修订**不得**降低既有环境变量模式与审计要求；上述条款的违反症状与复核方式随本节生效。
    - **违反时的症状**：引入托管模式后 env 模式被弱化（如允许明文）；审计预写被跳过。
    - **复核方式（可验证）**：env 模式回归测试保持全绿；审计预写失败用例保持不变；本节与旧版逐条对照无删除项。

### 资源使用范围约束

模型连接与通知渠道**必须**有 `scope`（`exclusive` / `shared`）与稳定所有者；运行时资格 = 共享 ∪ 本人专属；管理面可见性不受范围限制；范围转换**必须**检查其他 Agent、活动 Run 与消息路由，**不得**让其他使用者静默失效。

- **违反时的症状**：专属资源被其他 Agent 使用；范围转换令在跑 Run 或既有绑定静默失效。
- **复核方式（可验证）**：资源表与契约含 `scope` / `owner_agent_uid`；准入与调用按 `RunEnv.AgentUID` 判资格；范围转换测试覆盖其他 Agent 引用、活动 Run 与消息路由三类检查。

### 资源身份与绑定权威约束

Agent 定义是资源 UID 绑定的**唯一权威**；数据库绑定表是可重建投影；名称不是身份；同名重建生成新 UID；**不得**按同名补绑；复制、归档、恢复、导出**必须**完整携带绑定。

- **违反时的症状**：绑定表成为第二权威；重建投影丢绑定；同名重建被误当同一资源。
- **复核方式（可验证）**：删除投影后可由 `AGENT.md` 完整重建；同名重建用例生成新 UID；复制 / 归档 / 恢复 / 导出用例保留 UID 绑定。

## 开发工作流（Development Workflow）

- **固定人工 review 仅两处**：AI 生成 US 颗粒度文档、自检与独立 AI review 后交人审核；通过后 AI 自动执行 `/us-register N` 与 `/module-dev N` 的 spec / clarify / plan / tasks、任务比对、analyze、Loop 实施 / 验收 / 修复，不设置登记、tasks 或实现前的固定人工确认。收口由 AI 复跑 analyze、独立复核并汇总证据，再交人审核 US 收口；未收到实际决定保持待审核。**`/speckit-analyze` 仍是实施前阻断检查**，CRITICAL 清零前不得实施。已审范围内的派生或实现问题由 AI 修复，实质范围 / 公共契约 / 权限 / 验收变更返回模块卡评审修订，不能伪造批准
- **两层 Harness**：公共规则与门禁集中维护、各轮复用，US 专属行为、故障与边界验收写入每份颗粒度文档，并由 AI 派生执行映射。公共门禁与专属验收均须通过，独立复核是审核方式，不另列第三层；人工收口与机器检查的结论分别记录
- **交付口径**：每个 US 收口以「有可演示 Demo + 门禁全绿」为准（**不**列为原则，是本节的工作流定义）
- **门禁**：`make check`（= `fmt lint sec test test-integration cover build` 七目标聚合）全绿是完成的定义。三条实测纪律：① `gofmt -l` / `gofumpt -l` **必须先查退出码、再判输出**（语法错误 → 非 0 退出；格式差异 → 退出 0 但输出非空）；② `-race` 需 CGO 开启，与 `CGO_ENABLED=0` 发布构建**分属不同命令 / job**；③ `-tags=integration` 默认不跑，**必须**单列
- **覆盖率底线（必须有可执行判据）**：`core` / `tool`（沙箱）/ `memory` / `storage` ≥ 70%，其余 ≥ 50%。`go test -cover` 只打印百分比、**不会**因低于阈值而失败——**必须**由 US-1 交付的覆盖率检查脚本（`make cover`，纳入 `make check`）按包解析结果并判失败。判定口径：**有可执行语句但无测试文件的包**（`no test files`）计 0%，未达标即失败，**不得**豁免；**无可执行语句的包**（`coverage: [no statements]`）跳过（无从测量，不计通过也不计失败）。安全关键路径（沙箱三档、凭证红线、审计落库）**必须**有专项测试，不靠覆盖率兜底
- **plan review 由 AI 执行，必查**：依赖方向无环 / 审计写入路径唯一 / 无框架坐标 / 无 `context.WithValue` 业务态 / 单二进制构建通过
- **原型五链路验证（2026-10-15 修订：分阶段执行，**不**阻塞后续 US 开工；裁决全文见起步手册 §4「已决（口径丙）」）**：①`go.mod` 坐标经 goproxy.cn 实测（US-1 内完成）；②链路 5（崩溃恢复 + 实例锁）由 US-1 小探针先验（不入库，内存 SQLite）；③链路 1 / 3 / 4 在 US-4 交付后立即验证（含链路 5 的真实实现复验）；④链路 2 的 HTTP 准入面（409 / 429）到 US-9 补齐。**契约状态**：运行时契约四件套在**对应链路**验证通过前均为**待验证设计草案**（状态头见各契约文件）；US-2 / US-3 在草案状态下开工属**预期安排**，**不构成硬前置阻断**。**最终冻结条件**：五链路全部通过 + 实测偏差回写 `contracts/`
- **提交纪律**：AI **不得**自动 commit / push / tag，提交时机由用户决定；提交信息 = Conventional Commits 标题 + 四段正文（Problem / Design / Testing / Impact）

## Governance

- 原则约束以经采纳的宪法为准；实现设计在四份权威文档之间以技术方案为准；数据结构与 API 固定字面量以对应契约为准。冲突涉及原则变更时，**必须**走宪法修订程序
- 宪法正式文本的修订**必须**经用户确认——AI **不得**自行修订；修订走 `/speckit-constitution`
- 版本策略：SemVer（MAJOR = 原则增删 / 重新定义；MINOR = 新增或实质扩展；PATCH = 措辞澄清）；每次修订同步更新顶部 Sync Impact Report
- 合规审查：每个 US 收口逐条自查十大原则与架构约束；`/speckit-analyze` 将宪法冲突判为 CRITICAL——**必须**调整 spec / plan / tasks，**不得**稀释原则
- 文档纪律：四份权威文档各司其职，**不得**互相"修正"；有冲突先裁决（技术方案最权威）再动手
