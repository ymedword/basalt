# Agent Harness

Harness 持有“做对了”的判据，Loop 使用工具取得证据，再决定修复、推进或停止。
本 skill 是可跨项目的验收方法；产品契约、命令、门槛和状态由项目适配文件提供。
支持 `design <任务>`、`verify <范围>`、`close <任务>`；自然语言等价请求也适用。

## 接入项目

1. 读取用户指令、项目规则、现有工作区状态和任务输入，保留已有变更及真实批准。
2. 发现项目已声明的适配文件；本 skill 的默认约定为 `harness/project.md`。
   若尚不存在，按 [适配模板](references/project-adapter.md) 建立最小映射；不为使用本 skill
   另造技术栈、目录、数据库或执行器。材料尚未确定时先设计，不凭占位参数开始实现。
3. 按需读取 [判据设计与故障验收](references/acceptance-design.md)，不要每轮加载全仓文档。
4. 默认固定人工 review 为任务卡生成后与交付收口时；项目明确采用其他策略时按其已授权
   流程映射。范围内派生和修复由 AI 推进，不重复索取任务清单批准。

整个 skill 目录可复制到其他项目的 skill 搜索目录，再建立该项目自己的适配文件。
保留最小 `name` / `description` 元数据，工具权限、模型选择和平台特性由运行环境配置。

## 两层 Harness

| 所有权 | 定义什么 | 任务卡如何使用 |
| --- | --- | --- |
| 公共层 | 安全 / 架构约束、检查命令、结果格式、验收变更和恢复规则 | 引用项目的单一事实源，不抄一份可能漂移的清单 |
| 专属层 | 当前任务行为、接口、故障、边界、反例和受影响回归 | 写进任务卡，绑定测试、命令、超时、保护路径与证据 |

单元、集成、端到端、故障正确性和性能是验证深度；快速反馈与外部验收是执行节奏。
它们都在两层 Harness 内组合，不是新增第三层所有权。不是所有任务都需要集群或压测，
不适用时写明依据，不虚构项目不存在的能力。

## design：先立判据

先核对任务卡的六类输入：功能、交互时序、接口、字段 / 类型 / 约束、可判定结果、
允许范围与停止条件。接口按项目实际情况使用函数、CLI、文件格式或网络 API。

设计每项验收时回答五问：

1. 最怕出现哪种失败？先列故障与不变量，再挑测试，不用覆盖率数字替代。
2. 应在哪一层验证？算法用单元，真实依赖用集成，装配用端到端，时序风险用受控注入。
3. 判据能否自动判定？明确对象身份、集合、内容、次数、状态和时间窗口；不能只看日志。
4. 每轮跑还是交外部环境？给快反馈、完整验收及重型验收分别绑定命令和预算。
5. 谁保护判据？实现者不能自行删除断言、增加跳过、放宽阈值或改预期结果。

每个关键不变量要有反例或逆改点；测试必须真的命中并因预期行为失败，编译错误、空匹配、
依赖缺失不算有效红态。纯新增功能可以先有接口缺失红态，但实现后仍须取得行为判别证据。
保留项目已有覆盖率底线，同时检查它是否遗漏关键失败模式。

作者自检后做独立 AI review，提交 findings、处置、未覆盖面与所审输入指纹；如无法获得
独立上下文，标明隔离限制。人工 review ① 审目标、风险设计、边界和验收，不能用 AI
自检或“默认推荐”伪造人审通过。

## 开发循环交接

已审输入由项目流程派生 spec / plan / tasks 并做一致性分析，随后使用相邻的
[loop-programming](../loop-programming/SKILL.md) 驱动实现、真实验收、修复与恢复。
本 skill 持有判据设计、验证与收口方法；Loop skill 不复制或改写判据来使实现通过。

## verify：把部件拼成真实链路

在能力具备后立即验证最小可交付链路，再验证新增入口和候选发布的完整装配。
核对入口请求、关键状态、真实依赖、外部动作与审计 / 可观测记录的同一关联身份；
部署启动、管理界面和日志查询也要能观察到同一次任务，不能仅证明各模块单测成功。

按需在明确窗口注入失败：确认持久化后、动作发出前后、终态提交前、取消与关闭交叠时。
采用屏障、可控时钟、代理或自有子进程，记录触发条件、种子、预算、恢复与清理。
先跑确定性最小反例，再做重复 / 随机试验；有限试验提供证据，不声称数学证明。
只操作本轮拥有的测试资源，故障注入不获得破坏共享或生产环境的授权。

外部 CI 的验收环境和策略若与实现者共享写权限，就不能声称判据已形成权限隔离。
权限、可信基线、制品指纹与实际 CI 结果分别核实；待外部报告时记未验证，不推断绿态。

## close：向人工 review ② 交付证据

独立 AI 复核原始输入、diff、调用方和验收，范围内问题自动修复并重验。真实目标、权限、
公共契约或验收语义需要改变时回到 review ① 修订，不将有风险的设计选择偷偷变成实现细节。

收口包包含：实际实现与交付范围、输入 / 源码 / 制品版本、必跑检查及退出码、专属不变量
证据、整链路与外部验收、发现处置、跳过原因、未覆盖面和下一步。通过、失败、跳过、
未运行分别呈现，机器通过不替代人审、真模型或真实服务验证。
等待实际人工收口决定后记录接受、退回或有条件接受；提交、推送和发布遵循已有授权。
