# 失败模式、验证深度与整体验收

## 先写不变量，再选择验证层次

| 深度 | 适合证明 | 不能代替 |
| --- | --- | --- |
| 单元 | 纯逻辑、编码、校验、状态转移、预算边界 | 真正的数据库事务、进程和网络行为 |
| 集成 | 真实存储、协议、进程、权限与资源生命周期 | 多入口、部署、跨模块的完整数据流 |
| 端到端 | 从实际入口到持久状态 / 下游结果的整条链路 | 故障窗口下的正确性、所有生产负载 |
| 故障正确性 | 崩溃、暂停、超时、断连、分区、接管和旧持有者恢复 | 无穷时序的形式证明、尚未实现的集群能力 |
| 性能 / 压测 | 已定义负载下的吞吐、分位延迟、集中到期和资源变化 | 数据正确性、权限边界与副作用语义 |

层次按风险选择；分布式性质也需要单元 / 模型测试与真实故障试验共同支持，不能将
“纯逻辑用单元、正确性只靠混沌”当成互斥规则。没有集群的任务不要求伪造多节点层。

## 一条专属验收的最小表达

```text
失败模式 → 必须守住的不变量 → 输入与观察对象 → 注入窗口 / 动作
        → 机器断言 → 时间预算 / 重复方式 → 清理与证据 → 对应任务
```

断言至少检查适用的维度：

- 身份与集合：收到的 ID 集合与已确认集合一致，不能只比较条数；另检查重复次数。
- 内容与关联：负载、状态、请求 / Run / 调用身份一致，不能用“出现成功日志”代替。
- 时序与进度：从定义的故障或触发点测量，成功条件满足后再断言；不用任意缩短等待造绿。
- 禁止动作：拒绝路径需要证明外部请求 / 文件写入 / 进程启动没有发生。
- 恢复与清理：恢复后状态可解释，旧持有者不能继续提交；测试资源可被本轮清理。

“已确认接受后最终完成”“至多一次外部动作”“不重放不确定调用”是不同契约。
先选择真实业务语义再写断言，不给所有项目套用无丢失或 exactly-once 承诺。

## 将最坏时刻转成可重复步骤

| 风险窗口 | 可控注入方式 | 应收集的证据 |
| --- | --- | --- |
| 接收确认前后 | 存储提交屏障、失败事务、进程退出 | 哪些请求被确认、哪些持久化、恢复后如何处理 |
| 外部动作成功但结果未提交 | 下游接收器确认后阻断提交 | 实际动作集合、pending / unknown / 终态、重试责任 |
| 父任务取消与并发回调 | context / 等价取消、屏障同步 | 返回身份、剩余进程 / goroutine、审计终态 |
| 所有权移交 | 暂停旧进程、阻断续约、恢复旧持有者 | 归属代次、有效写入 / 动作、旧提交被拒绝 |
| 网络与依赖波动 | 自有测试代理的断连、延迟、丢响应 | 请求是否发出、是否重复、超时与恢复路径 |

优先使用可控时钟、屏障、真实临时库、进程和下游接收器，不只靠概率命中。
随机 / 重复试验记录种子、注入点、次数、负载和失败轨迹；稳定重放已发现的最小反例。
容器 kill、网络分区和压测只在本轮拥有的隔离环境进行，不能把 host 网络修改当普通单测。

## 快反馈与独立外部验收

快速检查进入每轮实现 / 修复；重型 E2E、部署矩阵、故障注入或压测按项目风险进入
里程碑或发布验收。关键故障的廉价确定性反例可以每轮跑，不能将所有故障测试都推迟。
整体验收将部件与运行环境拼起来，核对实际入口、依赖、状态、结果和观测面；“所有
单元测试分别绿”不是整链路通过。缺失必验外部证据时保持未验证并影响收口判定。

CI 作为外部判据，需要核实实现者对验收定义、受保护分支与执行身份的写权限；
同一分支里的一份 workflow 文件不是自动的权限隔离。保护语义与实际强制机制分别记录。
仓库内哈希 / protect 检查能发现漂移，但同权限进程可同时改程序和判据，不能称恶意隔离。

允许添加开发单测和在批准接口下适配夹具；禁止实现者通过删测试、改基准、扩大 SKIP、
降门槛、改时间预算等方式改变验收语义。测试确实错误时，验收所有者给反例、变更影响
及等价性说明；实质语义变化返回任务卡人审，不让实现者自行批准。

## 启动 Loop 前的五问

失败模式列全了吗？层次合适吗？断言可判定吗？快 / 重执行时机清楚吗？判据由谁保护？
任一项缺证据时先补 Harness，不能以覆盖率、测试数量或最终回复自信程度替代。
