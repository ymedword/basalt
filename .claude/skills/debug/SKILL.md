# debug — 四阶段根因定位

## User Input

```text
$ARGUMENTS
```

## 适用范围与边界

- **适用**：本仓库开发期问题——测试失败、行为与颗粒度文档不符、构建 / 门禁报红、
  集成异常、间歇性故障的排障。
- **不替代 `/module-dev`**：修复涉及交付物（新方法 / 新字段 / 新依赖 / 公共接口）
  时，写码的软 / 硬门禁照 `/module-dev` 执行；本 skill 只管「找到根因 + 最小修复」
  的方法与取证。
- **不自动** commit / push；**不得**改测试判据让红变绿（测试纪律见
  `docs/DevelopmentLoop.md` §6.2）。

## 总则（不可违背）

1. **不得**在根因调查完成前改代码——「先猜着改改看」是本 skill 要消灭的行为；
   「找不到根因」多数是调查不完整，不是真的没有根因
2. 一次**只验证一个假设**；假设失败 → **换**新假设，**不得**叠加「顺手一起改」
   （症状：改了三处，不知哪处起作用，还可能引入新问题）
3. 同一问题修复 **3 次不收敛 → 停**：**不得**第 4 次盲修，与用户讨论是不是
   设计 / 架构问题。「同一问题」的定义 = 测试名或首错位置 + 症状短语；计数
   来源 = 当前 feature 的 run-state.md 失败台账（module-dev「运行状态文件」节），
   跨会话从台账恢复；无台账 → 本会话计数并在报告标注**未持久化**
4. 修复**必须**先有能复现的失败测试（红）再实现（绿）；测试覆盖不到的问题，
   先补测试再修
5. 「修好了」**必须**有本轮当场证据（命令 + 输出 + 退出码）——跑过全量门禁与
   相关回归才允许表态（完成证据纪律）
6. 改动越出本问题范围（新依赖 / 新概念 / 动公共接口）→ 按 `/module-dev`
   软门禁**停车**等用户裁决

## 步骤 0：先查已知坑

扫 `docs/DevelopmentLoop.md` §7 陷阱表（每条带「怎么发现」与「怎么复核」）：

- **命中** → 按该条的「修复与复核」路径走，并跑它的复核命令确认真修掉；
- **未命中** → 进四阶段。

## 四阶段（每阶段有退出判据，未达不得进下一阶段）

### 阶段 1：根因调查（禁修）

1. **读原始证据全文**：报错原文 / 完整堆栈 / 测试完整输出——**不得**只看摘要
   或转述；
2. **稳定复现**：缩成一个能反复跑的**最小命令或失败测试**（先让它红）；间歇性
   问题的触发条件与频率如实记录——「跑一次没复现」不等于不存在，**不得**据此
   下结论；
3. **查最近改动**：`git log --oneline -15` 与 `git diff`——上次全绿到现在改了什么；
4. **多组件 / 跨进程问题**：先在边界加**诊断埋点**取证据（临时日志 / 打印）再
   分析，不许隔空猜哪一层坏；诊断代码**不得**进提交，事后必删（run-state.md
   不受此限——它是过程状态文件，收口不删）；
5. **反向追踪**：从报错点沿调用栈往回找到**第一个**错误产生的位置（而不是它
   最终爆出来的地方）。

**退出判据**：能说清「第一个错误发生在哪个文件哪行、为什么会发生」。

### 阶段 2：模式分析

1. 找**能工作的**同类样例（同包测试 / 前序模块的相同模式 / 标准库用法）；
2. **完整读**参考实现——不跳读、不凭记忆；
3. 列出样例与问题代码的**每一处差异**，逐条问「这处差异是不是根因」。

**退出判据**：可疑差异收敛到 1~2 处。

### 阶段 3：假设与验证

1. 写下**一个**具体假设：「我认为 `X` 导致 `Y`，因为 `Z`」；假设与结论**逐条
   追加**进 run-state.md 失败台账（一行一次尝试：日期 / 假设 / 结果 / 同题计数）；
2. 用**最小变更**验证（改一行 / 加一条断言 / 临时打印），一次一个；
3. 与预期比对：成立 → 进阶段 4；不成立 → **回到阶段 1** 用新信息重新调查，
   **不得**在旧假设上叠补丁；
4. 同一问题累计第 3 个假设仍不成立 → 触发总则 3，停下讨论架构。

### 阶段 4：修复

1. 先写 / 补**失败测试**（复现根因的最小用例），看它**红**——必须看到**逐字的
   预期失败文案**，不得只看退出码或"报错了"（逆改后变红 ≠ 判别力成立）；
2. 最小实现修复，看它**绿**；一次一改，不做无关清理；
3. 跑全量门禁（配置区）+ 相关前序模块回归；
4. 输出**变更总结**（改动点 / 重点 review 清单 / 判据面变更 / 如何验证——与
   `/module-dev` 步骤 7 同构）：写明根因与修复的逐条对应关系。

## 修复后的收口

- **回写 run-state.md 台账**：本次尝试次数与最终结论（成立 / 推翻 / 待确认）；
  结论推翻时**更新并写明依据**，**不得**删旧行；红态 / 绿态读数（命令 + 输出
  摘要）一并记录；
- 修复落在某 US 范围内 → 回归 `/module-dev` 的收口口径，证据进该模块验收报告；
- 修出了新的坑（教训可复用）→ 按陷阱表惯例拟一条（带「怎么发现」与「怎么
  复核」），**经用户确认后**再入库；
- commit / push 归用户——全程不自动执行。

## 项目配置区（复制本 skill 到新项目时只改本节）

- 门禁命令：`make check`（= fmt lint sec test test-integration cover build 七目标
  聚合；Makefile 由 US-1 交付，未落地前按 `docs/DevelopmentLoop.md` §2.2
  命令序直跑）
- 项目纪律：`docs/DevelopmentLoop.md` §6.2（测试纪律 / 完成证据 / 审查回执）；
  陷阱表 §7
- 本机纪律：`GOPROXY=https://goproxy.cn`；`go test -race`（需 CGO）与
  `CGO_ENABLED=0` 构建**分属不同命令**；build tag 集成测试须 `-tags=integration`
  单跑
- 可观测性双轨：失败路径**同时**要审计落库与 WARN 日志（只落其一 = 排障黑洞）
