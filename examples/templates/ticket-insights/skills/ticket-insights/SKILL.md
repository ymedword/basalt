# 工单洞察技能（L2 正文）

这份技能规定「怎么分类、怎么计数、怎么写」。取数由 `AGENT.md` 的步骤完成，本技能
**不负责**读库、不负责判断工单重要不重要。

## 一、分类规则

对每条工单只看 `subject`，按下面的顺序逐类匹配，**首命中即定类**（后面的类别不再
检查）：

| 顺序 | 分类 | 关键词（命中任意一个即算） |
| --- | --- | --- |
| 1 | 登录 | 登录、验证码、密码、账号 |
| 2 | 支付 | 支付、退款、到账、金额、发票 |
| 3 | 配送 | 配送、快递、物流、地址、发货 |
| 4 | 未分类 | 以上都没命中 |

为什么顺序固定：一条工单可能同时提到「登录」和「支付」（例如「登录验证码收不到，
导致支付一直失败」）。按顺序**首命中**归类，结果可复核；若改成「关键词最多者胜」，
同一份数据在不同模型上会得到不同分布，日与日之间就不可比。

**不得**做的事：

- 不得按情绪、紧急程度、客户等级重排分类；
- 不得把「未分类」改写成最接近的类别——它本身就是一条有用的读数（关键词表需要补）；
- 不得新增分类（新增就是改判据，要改成模板里的固定表并重跑夹具）。

## 二、计数口径

| 指标 | 定义 |
| --- | --- |
| 分类工单数 | 该类别下的全部行（不看 `status`） |
| 未关闭 | 该类别下 `status = open` 的行数 |
| 明细行数 | 本次查询返回的总行数（含未分类、含待确认字段的行） |

- 四类工单数相加**必须**等于明细行数；对不上说明漏了行，先查数据，不要改数字；
- `status` 只有 `open` / `closed` 两个合法值，其他值（含空串）计入「待确认」，
  且**不**计入未关闭；
- 不计算百分比、不算趋势——没有历史库可支撑这类数字。

## 三、报告固定模板

```markdown
# 工单洞察 · <观测日期>

## 来源
| 项 | 值 |
| --- | --- |
| 数据源 | <MCP 服务名 / 样例库路径> |
| 明细行数 | <n> |
| 观测时间 | <ISO 时间或「夹具复跑」> |

## 分类分布
| 分类 | 工单数 | 未关闭 |
| --- | --- | --- |
| 登录 | <n> | <n> |
| 支付 | <n> | <n> |
| 配送 | <n> | <n> |
| 未分类 | <n> | <n> |
| 合计 | <n> | <n> |

## 未关闭清单
- [<ticket_id>] <subject>（<channel>，<created_at>）

## 待确认
- [<ticket_id>] <哪个字段、什么值、为什么不合法>

## 失败
<错误原文；没有写「无」>
```

规则：

- 「未关闭清单」只列 `status = open` 的条目，按 `row_id` 升序；
- 没有内容的小节写「无」，不要省略——省掉一节会让读者以为漏跑了；
- 每条都带 `ticket_id`，方便回库核对；
- 不写「建议改进」「客户满意度推测」——这类内容库里没有，属于臆测。

## 四、失败与降级

- 查询失败：只写失败段，不写分类结论；
- 0 行：四个分类全写 0、合计 0，并写明「本次没有工单」；
- 字段缺失（`subject` 为空或 NULL）：按「未分类」计，并在「待确认」写明缺失；
- `tickets.json` 与查询结果行数不一致：先重落盘，仍不一致就停下写失败段。
