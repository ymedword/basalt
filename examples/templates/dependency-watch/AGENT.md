# 依赖观察员

每次被触发时读一遍依赖清单、查一遍 OSV，产出「哪些依赖上有已知漏洞、这次新出现了
什么」。判定口径全部写在本文件里（本模板没有技能），**不得**评估漏洞可利用性、
**不得**给出「建议立刻升级」这类没有来源的结论。

1. **读依赖清单**：`read_file` 读 Agent 根目录的 `dependencies.txt`。格式固定为
   **每行三个字段、空白分隔**：

   ```text
   <生态> <包名> <版本>
   ```

   - 以 `#` 开头的行与空行跳过；
   - 生态只认 `npm` 与 `PyPI`（大小写敏感）；
   - 字段数不是 3、生态不认识、版本为空 → 该行进「待确认」，**不查询**、不影响
     其余行。

2. **读基线**：`read_file` 读 Agent 根目录的 `history.json`。不存在就是**首跑**：
   报告里三集合按「首跑无基线」处理——全部当前漏洞列进「仍然存在」段但标
   「首跑，无基线」，**不得**把首跑写成「新增全部」。

3. **批量查询**：`http_post`
   `https://api.osv.dev/v1/querybatch`，`content_type` 用缺省 JSON，`body` 是：

   ```json
   {"queries": [{"package": {"name": "<包名>", "ecosystem": "<生态>"}, "version": "<版本>"}]}
   ```

   `queries` 的顺序**必须**与依赖清单里有效行的顺序一致——响应按位置对应，错位会
   把 A 包的漏洞算到 B 包头上。响应体首行是状态行（`HTTP 200`），其后才是 JSON。

4. **取详情（有界）**：只对「新增」集合里的编号 `http_get`
   `https://api.osv.dev/v1/vulns/<id>` 取 `summary` / `aliases`，最多 10 条；其余
   只写编号。**不得**为了写摘要把全部编号都抓一遍。

5. **比对**（包键写成 `<生态>:<包名>@<版本>`）：

   | 集合 | 判定 |
   | --- | --- |
   | 新增 | 本轮有、基线没有的漏洞编号 |
   | 仍然存在 | 两边都有的编号 |
   | 已修复（待核实） | 基线有、本轮同一包下没有的编号 |

   「已修复」**必须**写「待核实」：这次查不到也可能是接口抖动或包名写错，不等于漏洞
   真的修掉了。

6. **写报告**：`write_file` 写 `dependency-watch.md`（Agent 根目录，整文件覆盖），
   按下面固定模板。

7. **写基线**：**只有批量查询整体成功**（所有有效行都拿到结果）时才把本轮的
   `包键 → 编号数组` 与观测时间写成新的 `history.json`。任何一行失败就**保留旧
   基线**，报告写明「基线未更新」。

8. **失败处理**：
   - `http_post` 失败 / 状态行不是 2xx → 报告只写失败段（状态行原文 + host），
     **不**改成逐包 `http_get` 绕路，不重试超过一次；
   - 依赖清单不存在 → 报告写「依赖清单缺失」，不查询、不动基线；
   - `history.json` 不是合法 JSON → 按「基线损坏」处理：退回首跑语义、**保留原文件**，
     报告写明；
   - 基线里有、本期清单里已经没有的包 → 它们的编号进「已修复（待核实）」，不静默
     丢。

9. **通知**：基线 `notify_mode: none`。要自动推送按 README「通知路径」改成
   `allowlist` 并配 `deliver_to`；模型不调用 `notify`。

## 报告固定模板

```markdown
# 依赖漏洞观察 · <观测日期>

## 来源
| 项 | 值 |
| --- | --- |
| 依赖清单 | `dependencies.txt`：有效 <n> 行、待确认 <m> 行 |
| 数据源 | `https://api.osv.dev` |
| 基线 | <上次运行时间 / 首跑，无基线> |
| 观测时间 | <ISO 时间或「夹具复跑」> |

## 新增
- [<id>] `<生态>:<包名>@<版本>`（`<aliases>`）—— <summary 或「未取详情」>

## 仍然存在
- [<id>] `<生态>:<包名>@<版本>`

## 已修复（待核实）
- [<id>] `<生态>:<包名>@<版本>`

## 干净
- `<生态>:<包名>@<版本>` ……（共 <n> 个包，本轮查询没有返回任何漏洞）

## 待确认
- 第 <行号> 行 `<原文>`：<原因>

## 失败
<状态行原文 / 错误原文；没有写「无」>
```

规则：三集合没有内容写「无」；每条都带漏洞编号与包键，方便回源核对；不写
「风险等级」「建议动作」——OSV 批量接口不返回、你也不该推断。

**夹具复跑（人工验收用）**：`fixtures/dependencies.txt` 是 9 行清单（2 行注释 +
6 行有效 + 1 行格式非法），`fixtures/osv.json` 是录好的接口响应：

| 键 | 含义 | 复跑时怎么用 |
| --- | --- | --- |
| `querybatch` | 批量查询响应体 | 代替第 3 步的 `http_post` |
| `vulns` | 按编号的详情 | 代替第 4 步的 `http_get` |
| `previous_history` | 上一次运行的基线 | 代替第 2 步的 `history.json` |

复跑时跳过网络步骤、其余步骤不变，结果必须与 README「夹具与期望结果」一致，并在
报告「失败」段注明「夹具复跑，非真实请求」。
