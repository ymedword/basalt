# 采购响应准备工作流（US19 演示）

这是内部售前／采购材料准备案例。48 条需求与企业材料均为明确合成，产品材料固定到
`source-manifest.json` 中的 main 版本；开放许可采购指南仅作方法参考。
本案例不代表真实投标、客户项目、企业资质、性能证明或法律审查。

## 角色和交接

| Agent | 负责什么 | 交给下游什么 |
| --- | --- | --- |
| 采购需求调查员 | 分组核对原始要求、数字、起算点 | 12 项要求与原文来源，不判断供应商已满足 |
| 技术售前核查员 | 对照固定产品基线 | 已有能力、未支持项及技术证据缺口 |
| 商务交付核查员 | 核对维护、付款、人员和验收责任 | 商务／交付待办、责任角色和下一行动 |
| 标前复核协调员 | 用原文复核上游结论 | 四份完整矩阵及内部决策摘要 |

主工作流 17 个顺序节点，4 个章节组各覆盖 12 条需求。调查员读取第一章文件，第二章
冻结全文随输入传入；技术／商务节点取得固定资料全文与已验证的上游结构输出。
交接保留 `result`、`sources`、`open_questions`。修正演示 `fixed-matrix-v1` 的四个复核
节点另带 `statuses`，`result` 和 `statuses` 各含本组固定的 12 个条款编号。报告器
并列展示冻结采购原文与模型意见，不用模型改写的条款替代原始要求。最后摘要不能
替代四份 12 行矩阵；结构齐全仍需独立复核事实、来源与缺证边界。

分工价值来自资料权限、独立复核和可追溯交接；不能仅凭有多个 Agent 就宣称质量更高。
`bid-general` 是对照 Agent。三组对照分别为单 Agent 单 Run、通用 Agent 三阶段工作流、
专业 Agent 三阶段工作流。B/C 还存在 persona、知识集合和核心记忆差异，比较的是整套
配置，不能孤立归因为角色分工。三组配对小样本不支持统计或商业收益泛化。

## 知识库与记忆

三个隔离集合保存采购要求、公开产品基线、合成商务材料。每个角色只绑定其所需集合。
五份合成经验经原 Propose→Confirm 入口激活，沿原核心记忆路径注入；禁止全局记忆。
旧维护期经验必须让位于当前 18 个月要求。此处不演示归档记忆召回，不将新结论自动
写入共享事实。检索命中不等于读完全部材料，完整覆盖要看原文件及逐项矩阵。

修正长任务只在显式 `prepare-matrix` 后收窄商务与最终复核 Agent 的自动检索绑定：
这两类节点已获得本组冻结原文全文，避免反复向量化逐渐增大的上游报告。需求与技术
节点继续使用知识库，全部已确认核心记忆保留。旧角色文件和三组对照回执保持原样；
新配置、新固定版本和新任务分别记账，不能把新结果回填到旧对照。

## 管理台走查

1. 进入“工作流”，区分“工作流定义”和“执行任务”；选择“新建工作流”。
2. 填写目标、约束及任务参数，从已就绪 Agent 中添加节点，定义输出字段，再选择
   上游字段作为下一节点输入。调整顺序应同步连线；无效引用应阻止校验／发布。
3. 在线校验后，在页内核对影响并发布；填写任务参数启动，查看每个节点的原 Run、
   调用审计与最终产物。格式通过不等于业务结论通过。
4. 打开本案例的执行任务，核对 48 条原始要求、四组矩阵、摘要和证据缺口。复杂嵌套
   Schema 的定义保留高级原文编辑；基础字符串／整数／布尔字段可直接表单编排。

## 本仓开发验收工具

这些脚本仅用于显式启动的隔离开发夹具，不是线上部署入口，不含生产凭据。
`start-review.ps1 -AllowAuthorizedRealModel` 需要本地受保护凭据及明确费用授权。
启动前先核对 `source-manifest.json`、模型计价和全局剩余额度；不能直接复制此历史授权
作为未来新的付费许可。密钥只进入本机网关进程，不进入 Agent 工作区、提示词或报告。

按顺序运行 `scenario.py` 固定资料、启动夹具，随后使用 `demo.py setup`、`ingest`、
`publish` 和 `run <label>` 操作原产品 API。所有请求、失败和预检共用 `.loop/` 下的一份
预算账本；已记录的运行 label 拒绝重放，未确认的导入／用量必须只读对账。
`collect.py <label>` 只读取原 Run，将原响应、哈希和矩阵收集到
`.loop/us19-business-output/<label>/`；它不调用模型，不修饰原结论。

修正长任务使用 `demo.py prepare-matrix`、`demo.py publish-matrix`，随后在剩余模型
授权足够且预检通过时显式执行 `demo.py run long-fixed-v1`。前两步只更新隔离配置／
发布定义，不执行模型。原 setup、导入和旧任务无需重做。运行回执显式记录
`fixed-matrix-v1`；collector 按回执选择格式，旧回执仍按原三字段 Markdown 规则
判定。未知发布或配置写入结果停止重发，保留原请求供只读核对。

`test_budget_gateway.py`、`test_demo.py`、`test_collect.py` 均为离线回归。
真实模型结果另见本轮 `specs/019-flow-collaboration/run-state.md` 及所引原始报告；
静态 stage、脚本模型和 JSON 结构检查不替代真模型业务结果。

用户于 2026-11-04 批准按多阶段、结果完整可用、最长 30 分钟验收，不设最低时长，
不用等待凑时长。预算停止或业务复核失败须原样报告，不能算作目标已达成。
同日累计 Chat 授权由 90 提高至 115 次，其余总限额不变；网关须显式传入
`--authorized-chat-limit 115`，沿用原账本，未知用量不得借追加授权清零。
随后用户批准在离线修复通过后将累计上限由 115 追加至 125 次，仅再完整复验一次。
须沿原账本显式传入 `--authorized-chat-limit 125`；`demo.py run long-fixed-v2`
固定使用原 `long-fixed-v1` 已发布的定义与版本，原失败任务和全部消费继续保留。
每个根任务仍受 200000 tokens、
70 次工具和 1800 秒上限；外层总授权不能替代根任务预算。
