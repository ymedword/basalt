## 1. 第一阶段基线与挂载点

截至本文档建立时（2026-10-15），仓库处于**纯文档态**：四份权威文档 + 兼容性三件套已就位，14 个 US 已递进式分解（[DemandAnalysis.md](DemandAnalysis.md) §1.5），`v0.1.0` 尚未开工。

评估「未来规划是否可行」的关键不是想做什么，而是**每条新路有没有现成接口缝**。第一阶段方案按「接口先行、实现分档」预留了下列缝，即增量阶段的**挂载点**：

| 挂载点（预留缝） | 现状（设计态） | 指向的方向 |
| --- | --- | --- |

## 2. 中期目标

1. **补齐能力版图**：五个扩展面（需求文档 §1.2）各推进一档——渠道双向、工具策略、记忆语义化、治理层、隔离升级。
2. **单机 → 分布式**：存储可插拔，以多节点分摊定时 / 后台 Agent 任务、触发去重和故障恢复切入；任务领取、会话串行与恢复归属改由数据库协调（技术方案 §4.6 / Compatibility §4 第 3 条；首版边界见 §5.5）。
3. **让 Agent 越用越聪明**：审计三表 → 成功轨迹蒸馏为技能 / 记忆草案，人在环上入库。
4. （长期定性）对接 **A2A** 等开放标准——MCP（工具协议）已在第一阶段落地（US-7，技术方案 §6.5 / §11），不再是「长期方向」；A2A 属长周期方向，**不得**作为近期里程碑排期。

## 3. 方向评估（A–I）

> 每方向五要素：**挂载点**（已有缝）/ **触发信号**（什么时候才动手——信号没出现不拍脑袋）/ **主要新增** / **卡点与冲突** / **判定**。字母编号**沿用 NivroOS 规划**，使两份 Roadmap 可逐字母互引——**不是** US 编号，也不构成承诺。条目「文档依据」逐条指回本仓原文；**C / D / I 承接自 NivroOS 规划**（本仓文档未预先承诺，立项前**必须**按 §9 取数纪律用本仓事实重新评估）。另有技术方案 §4.3 明示的「核心阶段不做」五项（工具并行调用 / Agent 间委托 / 上下文总结压缩 / 流式响应 / 准入排队）——它们不是独立方向，是各方向实施时的子项或独立裁决题，本文档不再单列。

### A — 状态外置与分布式底座

- **挂载点**：仓储接口定义在消费方（`core` 声明 / `storage` 实现）；会话、审计、定时任务状态已在 SQLite；`TaskStore` 依赖倒置。
- **触发信号**：单节点撑不住或需要高可用；出现集群交付要求（K8s 清单 / Helm / 多副本——需求文档 §6「环境适配」）。
- **主要新增**：存储可插拔（首版优先 PostgreSQL，MySQL 留作后续适配候选）；实例无状态化（会话 / 记忆 / 审计 / 任务状态外置）；基于数据库表的任务领取、租约与分布式会话串行；Agent / 技能 / 记忆等文件资产采用共享存储或版本化分发（PVC / NFS 的可行性须验证，**不得**通过共享 SQLite 库文件实现多节点协调）。
- **卡点与冲突**：会话锁与崩溃恢复是**进程内**语义（OS 级独占文件锁 + 心跳仅诊断，技术方案 §4.6）——多副本下锁载体**必须**重新设计（§5.5）；`schema.sql` 是手工幂等脚本、非方言中立，迁移**不得**依赖自动 DDL（原则 9 本来就无 ORM）；Agent 目录是文件系统语义，「丢目录即上线」在多副本下依赖共享存储设计。
- **判定**：可行；**必须与存储迁移同批**；是 B 的向量宿主候选（与 B 共享同一外部存储实例）。**首版采用数据库表协调的调度型架构，不引入 etcd**，故障接管以几十秒级为规划目标；领取互斥、执行恢复与业务副作用去重分别验收（§5.5），选型理由与再评估条件见 §5.5.4。本项仅约束扩展阶段 A / M3 的规划，当前核心阶段仍按 SQLite 单实例交付。
- **文档依据**：IndustryResearch §6 第三阶段；需求文档 §6「环境适配」；Compatibility §4 第 3 条；技术方案 §4.6。

### B — 向量记忆与知识库

- **挂载点**：`MemoryService` 门面背后换实现（三档载体换一行配置）；技能库「按名引用 + 渐进披露」是知识库的形态参照。
- **触发信号**：关键词检索找不准（`recall_memory` 是整串匹配、只认连续子串，词一分散就不命中——AiProgrammingGuide §7 陷阱 11）；记忆量大；知识分散在文档里靠人翻。
- **主要新增**：embedding 调用（走 Provider 显式映射）；向量存储；知识库（Compatibility §4 第 7 条口径：「向量记忆与知识库」）；记忆升级为语义检索。
- **卡点与冲突**：向量宿主先于 A 落地时需过渡方案（SQLite 侧过渡 or 随 A 引入外部存储——§5.1 待裁决）；**单二进制纪律**：向量依赖**必须**过 `CGO_ENABLED=0` 这道门（纯 Go 库或外部服务）；「整串匹配」是当前**承诺契约**（"连续短语命中 / 分散词不命中"两态被测试钉住），升级 = 行为契约变更，先裁决再改。
- **判定**：可行且**建议优先**——依赖最少、用户可感知；与 A 共享宿主。
- **文档依据**：需求文档 §6「记忆进阶」；Compatibility §4 第 7 条；技术方案 §5.1（召回是关键词检索——向量化属扩展阶段的另一档能力）。

### C — Flow 编排与多 Agent（承接自 NivroOS 规划）

- **挂载点**：自实现 ReAct 循环（原则 1，保留定制空间）；「一个目录 = 一个 Agent」可平移到「一个目录 = 一个 Flow」。
- **触发信号**：单 Agent 任务链条过长、人工串联成本高；需要子 Agent 委托。
- **主要新增**：Flow 目录约定与执行器（节点 = Agent / Tool，边 = 数据流）；子 Agent 委托；A2A 对接；`execute_code` 代码化编排（多步流水线压成一次推理）。
- **卡点与冲突**：技术方案 §4.3 明示「核心阶段不做 Agent 间委托」——是范围边界，不是禁止项，但**必须**经 US 流程裁决后放开；`execute_code` 超出既有执行语义（Policy / Runner 两接口），见 §5.3；A2A 是新协议面，坐标与实现方式在 US 内核实。
- **判定**：可行；承接自 NivroOS 规划；`execute_code` 按独立安全专项设计，不与编排同批交付。
- **文档依据**：技术方案 §4.3（核心阶段不做项）；其余承接自 NivroOS 规划。

### D — 越用越聪明（自我进化，承接自 NivroOS 规划）

- **挂载点**：审计三表 day-one 落库 = 成功轨迹已积累；技能库结构（`.basalt/skills/<name>/SKILL.md`）与声明式绑定就绪。
- **触发信号**：手动维护技能 / 记忆明显漏事。
- **主要新增**：成功执行自动蒸馏为 Skill 草案；经验 → Skill / Memory 学习闭环；模板 Hub；兼容 agentskills.io。
- **卡点与冲突**：**与既有红线正面冲突**——技能库对 Agent 只读（「技能库不可写入」由代码常量拒绝，技术方案 §6.5）；**必须**先裁决「人在环上的入库通道」（§5.4），**不得**以「让 Agent 自己沉淀」为由放宽。另有**质量准入门禁**五项（逐条独立设计与验收，**不得**当实现细节顺带处理）：成功样本认定（run 终态「成功」的判据——仅 `completed` 还是含降级容忍）/ 授权与脱敏（蒸馏原料是真实轨迹，可能含凭证与个人信息）/ 固定评测集（草案入库前后的对照口径，否则「越用越聪明」无从验证）/ 人工批准（§5.4 通道的具体形态）/ 版本化发布与回滚（技能须有版本、可退回上一版）。
- **判定**：可行；前置裁决不可跳过；该通道与 H 的 HITL 同构，作为 H 的首个用例。
- **文档依据**：技术方案 §6.5 / §9.3（技能库对 Agent 只读）；其余承接自 NivroOS 规划。

### E — 全渠道与多模态

- **挂载点**：Notify 类型 → 适配器显式映射（US-8 交付 webhook / 飞书两档）；`AGENT.md` 的 `channels:` 字段；出站通知基础设施完整。
- **触发信号**：有真实 IM 双向接入需求（「在群里直接用」——需求文档 §6）；交互体验成为瓶颈（SSE）；出现看图 / 听声的业务场景。
- **主要新增**：入站消息通道（企微 / 飞书 / 钉钉 / Slack 双向——需求文档 §1.2 / §6 口径）；SSE 流式响应；Web 搜索 / 浏览器 / 视觉 / TTS 类新工具；实时语音。
- **卡点与冲突**：SSE 与现口径「不做流式（扩展阶段）」的差距**按 §5.2 的评估口径在 E 立项时定断**（同步 handler 边跑边 Flush 不触宪；只有引入异步管线才需宪法修订）；渠道合规口径待裁决（§5.6）。**入站不是「再加一个适配器」**——每个入站渠道都要做：请求验签 / 事件去重（平台重投不得重复执行）/ 身份映射（IM 用户 → 会话身份）/ **快速 ack**（如 Slack 要求 3 秒内确认，否则重投——执行与应答解耦即后台处理，与 §5.2 同源、须一并评估）。
- **判定**：渠道扩展成本低（适配器 + 一行映射）——**适合作为社区可认领面**；SSE 按 §5.2 的评估口径在 E 立项时定断。
- **文档依据**：需求文档 §1.2 / §6「IM Channel」；Compatibility §4 第 4 条；技术方案 §3.3。

### F — 执行隔离升级

- **挂载点**：Policy / CommandRunner 两接口自设计之初就是为这条留的（技术方案 §1.1 第 6 条）；需求文档 §1.2「隔离」行的扩展版面。
- **触发信号**：需要执行不可信代码；多租户（需求文档 §6「沙箱升级」）。
- **主要新增**：容器沙箱 → microVM（两接口各新增实现 + 装配切换）；可选 SSH 执行后端。
- **卡点与冲突**：**不承诺「接口不变」**——容器档可能要求接口本身扩展（技术方案 §1.1 第 6 条已改口径）；对不可信 MCP server 的隔离同属此列（技术方案 §6.5「MCP 的行为边界」）。
- **判定**：可行；实现类 + 装配映射即可，接口缝已留好；是 H（执行准入）的宿主。
- **文档依据**：需求文档 §1.2 / §6「沙箱升级」；技术方案 §1.1 第 6 条 / §6.5；Compatibility §4 第 6 条。

### G — 企业化与治理

- **挂载点**：需求文档 §1.3 既有定义——扩展阶段 = 企业级治理层（§6）；审计表已按可查询结构落库（Compatibility §4 第 8 条按语）。
- **触发信号**：走出内网；多人多团队共用同一实例；合规验收（需求文档 §6 各行触发信号）。
- **主要新增**：认证（API Key / JWT）与反向代理样例；多租户 / RBAC / SSO；完整审计查询 API 与页面、导出、留存策略；Tool Policy 与审批流；密钥轮换 / KMS / Vault；Prometheus 指标与分布式追踪（`MetricsRegistry` 换实现）。
- **卡点与冲突**：体量最大的一条产品化轨道；与「核心阶段内网假设」的边界需重新划线；按信号驱动，**不得**一次性全做。
- **判定**：可行，属「年级」工作量；建议按最小可用切片滚动落地（如 API Key + 审计查询先行）。
- **文档依据**：需求文档 §1.3 / §6（认证与接入 / 多租户与权限 / 完整审计 / Tool Policy / 可观测度量）；Compatibility §4 第 5 / 8 / 9 / 10 条；IndustryResearch §6 第二阶段。

### H — 企业底座独有能力（HITL 与数据飞轮）

- **挂载点**：工具执行的单一控制点（Policy / ToolExecutor——审批挂起的天然挂载位）；审计三表（成本治理原料）；Provider 显式映射（智能路由挂载位）；`MetricsRegistry`。
- **触发信号**：危险动作需要人工把关（生产 / 严监管场景）；出现评测 / 蒸馏需求（数据飞轮）；成本敏感。
- **主要新增**：HITL 分级审批（危险动作挂起 → 推送审批 → 批准 / 拒绝后续跑——推送可先行复用既有通知渠道）；审计 → 数据飞轮（评测 / 蒸馏）；成本治理与弹性休眠；智能模型路由。
- **卡点与冲突**：HITL 要动 ReAct 循环 / 工具执行控制流（技术方案 §4.3「核心阶段不做」的边界，实施范围经 US 流程裁决）；需求文档 §6「Tool Policy（含审批流）」是本方向在文档里的最近亲。**HITL 前置清单**（六项，逐条独立设计与验收、**不得**当实现细节顺带处理）：等待审批的**状态持久化**（挂起期间进程重启不丢）/ 审批者**身份与权限**（谁能批什么）/ **审批过期**（超时策略必须显式选——自动拒绝而非静默永久挂起）/ **重启恢复**（恢复扫描要认得「等待中」的 run）/ **预算计时口径**（挂起时长是否计入超时与成本）/ **批准续跑不得重复执行**已完成工具（与恢复同一纪律：[contracts/run-and-errors.md](contracts/run-and-errors.md) §4 按位置判定）。
- **判定**：可行且**差异化最强**，与严监管定位最对齐——建议优先于 G 的大切片。
- **文档依据**：需求文档 §6「Tool Policy」行（审批流）；技术方案 §4.3；其余承接自 NivroOS 规划。

### I — 任务发布与 Agent 团队（压轴，承接自 NivroOS 规划）

- **挂载点**：C（编排）+ H（HITL）+ G（治理）的汇合点。
- **触发信号**：出现「指挥一群 Agent」的真实任务。
- **主要新增**：协调者 + 专家 Agent + 评审 Agent；每个子 Agent 仍是「一个目录」；全轨迹落库可回放；逐 Agent 隔离 + 关键节点 HITL；有界迭代、可打断、可追溯。
- **卡点与冲突**：依赖面最宽，**不得**提前启动；验收口径承接 NivroOS 规划定性——「不追求最炫的自主涌现，追求企业敢用的可靠交付」。
- **判定**：可行，作为阶段收拢项。
- **文档依据**：承接自 NivroOS 规划（本仓文档未预先承诺）。

## 4. 增量推进机制：US 扩展、文档演进与版本锚点

> 本节把三个机制问题（2026-10-15 用户提出）落成正式条款：US 编号能否扩展、新方向如何按第一阶段同款流程立项、整体技术方案文档如何随版本演进并留存旧版。

### 4.1 US 是开放序列，不是固定清单

- 14 个 US 是**第一阶段基线**（`v0.1.0` 的交付范围），**不是编号上限**。US 是台账里的一行，不是嵌在文档里的固定清单；编号**只增不改**，历史 US 的语义永不重定义。
- 扩展阶段立项从 **US-15** 起顺延。**不预分配编号**：§3 的方向不占号，只有「写了颗粒度文档 + 登记进台账」才占号。
- 台账（`docs/us/REGISTRY.md`，随准备阶段落地）是**唯一登记处**，append-only，由 `/us-register N` 单一写入。这是 NivroOS 第一阶段教训的固化：编号曾分散在多个 skill 与多份文档的六处，每加一个 US 要手改多处、必然漂移；收敛为「台账一处写入 + 编排 skill 只留取数规则句」。

### 4.2 方向立项 = 第一阶段同款三步链（零新 skill）

扩展一个新 US **不需要新 skill**——第一阶段的三步链本身就是「逐 US 扩展」的机制，对编号 N 是开放参数：

```text
§3 的某个方向
  → /module-doc-gen N    生成颗粒度文档（六节；§3 交付物清单 = 落位到包，§2 = 架构影响与约束）
  → /us-register N       台账追加一行 + 三个能力判断题（新依赖坐标 / 新构建步骤 / 新机器可判不变式）
  → /module-dev N        specify → clarify → plan → tasks（固定停点）→ analyze → implement → 七项证据
```

- **唯一的取数规则增补**（随四个 skill 移植时写进 `module-doc-gen` 配置区）：台账查无且 N > 14 时，「章节来源」**必须**取本 Roadmap 的对应方向节为事实源，写进颗粒度文档头部，供 `/us-register` 派生；方向节与四份权威文档冲突时，**以技术方案为准**（不变）。
- **一个方向拆几个 US**：按第一阶段同款粒度原则——「每个 US 结束有可演示成果」（AiProgrammingGuide §1.3）；够独立演示的拆细，不够的不硬拆。
- 扩展 US 的**完成定义与第一阶段完全相同**（七项证据 + 门禁全绿 + 一个 commit，AiProgrammingGuide §5），**新增一条收尾动作**：架构性变更的文档回写（§4.3）。

### 4.3 文档演进：单一事实源 + 收尾回写

- **四份权威文档 + Compatibility + contracts 永远代表「当前最新」的完整设计**——沿版本**原地更新**，不复制旧版本副本。理由：复制即产生第二事实源，两份必漂移（与 [Compatibility.md](Compatibility.md) §6 引用纪律同构——同一事实只允许有一个家）。
- **旧版本的「备份」由 git 承担**：发版打 tag，`git show v0.1.0:docs/TechnicalSolution.md` 即 `v0.1.0` 时点的全文。**不得**在 `docs/archive/` 之类位置放旧文档副本；确需对外发版文档包 → 从 tag 导出，作 release artifact 附件，**不入库**。
- **回写责任落进每个 US 的收尾**——并入七项证据的第 7 项「变更导读」：变更导读里点名本 US 的回写项，回写随 commit 入库，未回写不得宣布完成。

  | 变更类型 | 回写目标 |
  | --- | --- |
  | 新增包 / 依赖方向变化 | 技术方案 §10.1（三条包纪律）+ Compatibility §2.8 对照 |
  | 新增表 / 列 / 迁移 | [contracts/schema.sql](contracts/schema.sql) + 技术方案 §9 |
  | 新增端点 / 信封变化 | [contracts/openapi.yaml](contracts/openapi.yaml) + 技术方案 §7 + 需求文档 §5 |
  | 新增配置键 / 凭证语义 | 技术方案 §8 + [Operations.md](Operations.md) + 需求文档对应节 |
  | 新增 Agent 契约 / 工具 | [contracts/agent-md.md](contracts/agent-md.md) + 技术方案 §11 |
  | 与基线的行为差异 | Compatibility §3 有意改变清单（**必须**带验收样例） |
  | 行为级裁决（不改文档的） | 该 US 颗粒度文档「已决事项」（历史快照不改写） |

- **历史快照纪律（按状态区分，不搞一刀切）**：**当前 US 的草案可修订**（`clarify` / `analyze` 调整内容、`implement` 更新任务勾选——这是流程要求，不是违规）；**已批准范围的变更必须经用户确认**；**完成验收后的历史设计与已入库的颗粒度文档不得静默改写**——后续裁决追加在对应 US 文档的「已决事项」段，或记入新 US 的文档（与第一阶段同一模式）。
- **发布前对账（可验证）**：里程碑收口时按上表 grep 对账一遍（新增表 / 端点 / 配置键在文档里有对应行，文档描述的东西在代码里存在）；差异即回写遗漏，修复后方可发版。

### 4.4 版本与备份的操作口径

- 版本线：`v0.1.0` = 第一阶段（US-1~US-14）；此后**每个里程碑收口发一个 minor**（§6）。版本号只有两个载体——构建注入（`-X main.version`，技术方案 §10.2）与 git tag。文档正文的写作规则：**禁止**手抄「当前版本」（「当前版本是 vX.Y.Z」这类表述随发版即腐烂）；**允许**两类引用——① **目标版本线**（把版本锚定到交付范围的规划性表述，如「`v0.1.0` = 第一阶段」）；② **历史 tag 引用**（如 `git show v0.1.0:docs/…`——tag 是已定格的事实，不会腐烂）。
- 「第一阶段是首个版本，后续版本更新整体技术方案文档，旧文档要备份」——**能做到，且正是 §4.3 的口径**：整体文档原地演进（读它 = 读到最新完整设计）；旧版本由 tag 定格（读旧文档 = `git show <tag>:docs/…`）。**唯一不做的是「每版复制一份文档入库」**——那是漂移的根源，不是备份。
- 前提动作（**2026-10-15 已完成**）：`git init` 与首个 commit（准备阶段第 0 步）已就位——§4.3 的「旧版由 tag 定格」自此成立（**首个 tag 仍待发版时由用户创建**）；各 US 的分支与 commit 节奏见 AiProgrammingGuide §1.3。

## 5. 硬前置与待裁决事项

> 以下六项**必须先于**对应方向落定。标「待裁决」的**必须**由用户裁决；涉及宪法修订的走 `/speckit-constitution`，AI **不得**自行修改宪法。

### 5.1 向量宿主与单二进制纪律（B 前置）

- **约束**：B 引入的向量方案**必须**过 `CGO_ENABLED=0` 这道门（纯 Go 库或外部服务；含 cgo 的向量库直接出局——破单二进制纪律即产品破位，原则 8）。
- **待裁决**：宿主选择——SQLite 侧过渡（B 先行），还是与 A 的外部存储同批（先 A 后 B）。前者快、后者省一次迁移。
- **复核（可验证）**：引入依赖后 CI 四平台交叉编译全绿 + 产物静态性断言（`file` / `ldd`）。

### 5.2 流式响应与原则 7（评估口径）

- **事实**：技术方案现口径「不做流式（扩展阶段）」；流式会引入第二套取消与背压语义（Compatibility §4 第 4 条）。
- **评估口径**（2026-10-15 澄清）：**同步 handler 边跑边 `Flush` 不触宪**——逐事件写出仍是同步执行模型（goroutine 不随请求增长、取消仍走 `context`），原则 7 不受影响；**只有引入异步管线**（独立 goroutine 编排 / 背压队列 / 执行与应答解耦）才触及原则 7、需宪法修订。两项判定放 **E 立项时**按实际设计评估，本文档不预先断言。
- **约束**：若届时评估结论是引入异步管线 → 原则 7（同步执行 + `context` 只承载取消）的修订**必须**走 `/speckit-constitution` 经用户确认；**不得**借流式引入 goroutine 编排框架。

### 5.3 执行语义扩展（F / C 前置，原则 6 扩展）

- **约束**：容器档与 `execute_code`（若立项）新增的「执行一个动作」语义（边界、超时、进程树、审计关联）**必须**先设计再实现；**保留**「经评审脚本的受控执行通道」（`shell.interpreters`：解释器只接受 `[<脚本路径>, <参数…>]` 形态、脚本须落在该 Agent `scripts/` 或技能库、`scripts/` 对模型只读——技术方案 §6.5 / [contracts/agent-md.md](contracts/agent-md.md) §5.2）——**不得**通过放宽解释器白名单引入任意代码执行。
- **复核（可验证）**：可执行名白名单**不得**放行 `bash` / `sh`（等于把解释层请回来，AiProgrammingGuide §7 陷阱 6）；解释器只走受控通道——shell 单测断言 `-c` / `-m` / `-e` 内联形态被拒、脚本越界被拒（AiProgrammingGuide §7 陷阱 35）；`Policy.Check` / `CommandRunner.Run` 的新实现各有独立测试。

### 5.4 自我进化的写通道红线（D 前置）

- **红线（现状）**：技能库对 Agent 只读（「技能库不可写入」由代码常量拒绝，技术方案 §6.5）；记忆载体在文件工具白名单之外——**不得**以「让 Agent 自己沉淀技能」为由放宽，也**不得**把技能库加进写侧白名单。
- **必须**：设计「人在环上」的入库通道——蒸馏出草案 → 人审 → 入库；与 H 的 HITL 同构，建议作为 H 的首个用例先行落地。

### 5.5 多副本的会话锁与崩溃恢复（A 前置）

- **事实**：会话锁是进程内的；工作区实例锁是 OS 级独占文件锁（同机多进程语义）；崩溃恢复「只有持锁进程做」（技术方案 §4.6，[contracts/run-and-errors.md](contracts/run-and-errors.md) §1）。
- **首版定位（2026-10-17 讨论落案）**：基于共享数据库表协调多个 Worker，分摊定时 / 后台 Agent 任务；优先 PostgreSQL，首版不引入 etcd。后续是否增加独立协调服务，按实际控制面需求重新评估。首版同时适配 PostgreSQL / MySQL 不作承诺，具体方言、表结构与依赖在 A 的 US 立项时冻结。
- **承诺边界**：任务持久化、触发去重、可恢复任务的故障接管。正在进行的模型调用、shell 进程或交互请求**不承诺跨节点原地续接**；业务结果是否可自动重试按任务及工具副作用分类，**不得**笼统承诺「重跑一次、业务无感」或端到端 exactly-once。
- **约束**：多副本下锁载体与恢复选主**必须**重新设计；文件资产采用共享存储时，其一致性与可访问性**必须**在 A 的 US 内用原型验证。节点心跳仅作健康观测，**心跳超时不证明旧节点已停止**（AiProgrammingGuide §7 陷阱 33）；执行归属的变更必须经权威数据库的租约与条件更新，并落实失权隔离。

#### 5.5.1 数据库协调与领取纪律

下表为规划概念，**不是已冻结的表名或字段契约**：

| 协调面 | 首版职责 |
| --- | --- |
| 节点登记与心跳 | 记录节点身份、启动代次与健康信息；诊断故障，不单独构成抢占执行权的依据 |
| 任务定义与下次触发时间 | 持久化计划、时区与触发进度；明确错过触发时补跑 / 合并 / 跳过的策略并留记录 |
| 逻辑触发与执行尝试 | 以任务标识 + 计划触发时刻建立唯一约束，保证同一触发点只创建一份逻辑执行；自动重试另记执行尝试，不伪装成新的计划触发 |
| 执行归属与租约 | 保存持有者、有效期与递增的归属代次；续期、到期领取和状态提交均受条件更新约束 |
| 会话与恢复检查点 | 同一会话的运行在集群内串行；消息、已完成工具组、审计与可恢复位置供新持有者读取 |

- **短事务领取**：采用行锁或条件更新（CAS）原子完成到期任务认领、触发去重与触发进度推进；提交后才执行 Agent。**数据库事务与行锁不得跨越 LLM 调用或工具执行**，不靠长事务持锁保护整次 Run。
- **租约与失权隔离**：租约有效期与续期采用数据库侧统一时间口径。新持有者取得新的归属代次后，旧持有者的状态提交必须被数据库拒绝；续期失败时停止发起后续动作。仅让旧进程「自行发现失权」不足以保证安全，外部副作用另按 §5.5.2 处理。
- **故障回收独立于 cron 周期**：按独立的租约回收频率发现并领取可恢复任务，**不得**让每日任务等到次日触发才接管；正常触发延迟、错过触发处理与故障接管时限分别设计和验收。
- **存储与部署边界**：任务、Run、会话与审计使用同一套权威状态存储；接管节点必须取得相应版本的配置、文件与记忆。数据库自身的高可用与备份另行设计，**不得**用多个进程共享 SQLite 文件代替分布式状态外置。

#### 5.5.2 恢复与副作用边界

- **按归属恢复**：只恢复已合法认领的过期租约域；**不得**在每个 Worker 启动时沿用单实例全表扫描，把他人仍在执行的 Run 或 pending 审计行改写为失败 / unknown。
- **按检查点接续**：已确认完成的工具组不重跑；未执行步骤在重新校验执行权后继续。允许安全重试的任务须有明确策略、次数与审计；不得默认从头重跑整个 Agent。
- **不确定副作用保留诚实状态**：对已发出但结果未知的 HTTP POST、通知或 shell 操作，优先通过目标系统幂等键 / 结果查询确认；不具备这些能力时保留 unknown，进入人工处理或显式批准的补偿流程。数据库领取互斥不能替代外部系统的业务幂等。
- **前置设计必须回答**：Run 与执行尝试的关联 / 实例归属 / 租约期限与续期频率 / 续期失败处理 / 归属代次与状态写入校验 / 集群内会话串行 / 检查点一致性 / 文件资产获取 / 恢复扫描范围 / 工具幂等能力；答案须在 A 的原型前落案。

#### 5.5.3 可验证目标与故障演练

- **接管目标**：在协调数据库可用、存在健康且已就绪的备用 Worker、所需文件资产可访问的条件下，工作节点故障后**几十秒级**完成归属切换并开始处理可恢复任务。具体时限、负载与统计口径在 A 的原型中确定；当前不冻结「10 秒内」或毫秒级实时承诺。
- **计时分开**：正常计划触发延迟、故障注入到新持有者开始处理的时间、任务最终完成时间分别记录；数据库自身故障、文件存储不可用与结果不确定的外部操作分别验收，不能计作已成功接续。
- **触发去重**：多 Worker 同时竞争同一触发点，只创建一份逻辑执行；错过触发按已定策略处理并有审计依据。
- **失权与恢复**：注入进程崩溃、旧节点暂停后恢复、网络分区及续期失败；证明只有合法持有者可提交状态，恢复范围不影响其他活实例，已完成工具组不重复执行。
- **外部副作用**：分别验证具备幂等 / 查证能力和不具备该能力的工具；后者的 unknown 状态不得被自动重放掩盖，不能以「业务基本无感」替代判据。

#### 5.5.4 首版采用数据库协调的理由与再评估条件

**选型依据（2026-10-17 讨论补记）**：结合业务时效、一致性要求与运维成本，优先采用能满足验收目标且组件较少的方案。以下是首版的工程取舍，能力与成本须经 A 的原型验证：

**设计参考**：借鉴 [XXL-JOB 官方文档](https://www.xuxueli.com/xxl-job/) 中共享调度数据库、通过数据库锁协调调度中心集群，以及调度与执行职责分离的思路。此处为架构思路参考；Basalt 的任务领取、租约与失权隔离、Run 检查点和外部副作用恢复以本节的独立设计与验收为准，不由参考项目的能力描述代替。

| 工程理由 | Basalt 首版的选择 | 必须保持的边界 |
| --- | --- | --- |
| 时效与场景匹配 | 定时 / 后台 Agent 任务以几十秒级故障接管为目标，先验证数据库轮询、短事务领取与租约回收是否满足要求 | 正常触发延迟单独验收；任务重试须满足幂等或安全重试条件，不能推导为「重跑一次都没关系」 |
| 减少组件与状态衔接 | 状态外置本已需要数据库，协调数据与任务 / Run 状态放在同一权威存储中，便于在短事务内保持一致；首版节省另建 etcd 协调集群及其监控、备份、升级与故障演练的成本 | 组件减少不降低一致性要求；租约、归属代次、失权隔离及恢复检查点仍须完整实现和验证 |
| 复用企业部署能力 | 企业已有合适的 PostgreSQL 服务时，可复用其部署与运维体系；MySQL 仍按 §5.5 的后续适配候选处理 | 复用前评估数据库权限、数据隔离、连接池、协调负载、容量与高可用条件，不假定所有企业都有可直接承载该负载的数据库 |

- **架构分类与高可用**：多个节点分担任务、共享数据库协调归属，属于基于共享数据库的分布式任务调度架构；数据库承担集中协调职责。多 Worker 的部署与数据库自身的高可用分别设计、分别验收。
- **时限依据**：故障接管时限由租约、回收频率、备用节点就绪情况和存储可用性共同决定，采用 etcd 也不直接构成固定时限保证；其 Watch 事件交付没有固定延迟上界（[etcd 官方 API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/#apis-to-consider)）。具体目标仍按 §5.5.3 在原型中验证。
- **再评估条件**：协调负载显著影响数据库业务读写、出现更低协调时延或大量 Watch 订阅需求、需要独立控制面或复杂分片选主时，先测量现方案瓶颈，再比较数据库方案的改进与 etcd 等独立协调服务的收益和运维代价；引入新组件须走对应 US 的设计与依赖裁决。

### 5.6 渠道合规口径（E 前置）

- **待裁决**：IM 双向通道圈定企业侧（企微 / 飞书 / 钉钉 / Slack——需求文档 §6 口径）；个人号通道**不得**进入交付范围。

## 6. 建议里程碑顺序

> 顺序原则：触发信号先到者先行（§3）、每步可演示（第一阶段同款纪律）、低耦合面留给社区（E / F）。下表是**推荐发布顺序**，可随信号调整；**技术硬依赖**另列于表后——两套清单分列：排进推荐顺序**不代表**硬依赖自动解绑，硬依赖的顺序由技术决定。

| 里程碑 | 内容 | 依赖与理由 | 可演示成果 |
| --- | --- | --- | --- |
| M0 收口 | US-14 发布收尾：三个每日 Demo 真跑、README / 官网就位、`v0.1.0` tag（用户手动） | 第一阶段正式收口 | 干净检出 → 编译 → 起服务 → 跑通一次对话 |
| M1 | G 治理最小切片：认证 + 完整审计查询 API | 需求文档 §1.3 的「扩展阶段」定义就是治理层；真实部署后最先到的信号 | 带 API Key 的多用户访问；按 run / agent / 时间检索审计 |
| M2 | B 向量记忆与知识库（宿主按 §5.1 裁决） | 依赖最少、用户可感知 | 记忆语义召回，不再受「整串连续子串」限制 |
| M3 | A 状态外置 → 基于数据库协调的分布式调度 | 与存储迁移同批；宿主可复用 M2（若 M2 已引入外部存储）；首版不引入 etcd | 多节点分摊任务、触发去重、节点故障后接管可恢复任务（按 §5.5 演练验收） |
| M4 | H HITL：危险动作挂起 → 推送审批 → 批准续跑（**可先于 C 独立交付**——审批挂在工具执行控制点，不需要编排就位） | H 差异化最强、与严监管定位最对齐 | 危险动作挂起待批 → 批准后续跑 |
| M5 | C Flow 编排与多 Agent | H 就位后两者合体即 I 的骨架 | 多 Agent 流水线 |
| M6 | E 全渠道 + F 容器沙箱 | 低耦合，适合社区认领（F 相对 D 是硬前置，见下） | 企微 / 钉钉双向接入；容器内执行 |
| M7 | D 自我进化（等 §5.4 裁决）+ G 剩余切片（按信号） | D 前置 = §5.4 **且容器隔离（F）先行**；G 按客户信号滚动 | 成功轨迹蒸馏出技能草案，人审入库 |
| 收拢 | I 任务发布 + Agent 团队 | 前置全部就位 | 一句话任务 → 团队协作交付 + 全轨迹回放 |

**技术硬依赖（不可调；与上表编号无关）**：

1. **B 的向量宿主与 A 同批裁决**（§5.1）——宿主定了才谈 M2 / M3 的先后。
2. **D 的前置裁决不可跳过**（§5.4）——写通道红线未落定，D 不得开工。
3. **D 须容器隔离（F）先行**——自我进化 = 机器批量产出可执行物（技能草案可能带脚本），执行面必须先有隔离，否则「自动沉淀 + 直接执行」连成一条链。⚠ 这条把 F 从「社区可认领的低耦合面」升为 **D 的硬前置**：F 若推迟到 D 之后，D 必须整体推迟（F 相对 E 仍可并行，两者互不依赖）。
4. **I 严格最后**——前置全部就位才启动。

顺序总览：

```text
M0 收口 ─▶ M1 G 治理最小切片 ─▶ M2 B 向量（先定宿主）─▶ M3 A 分布式底座 ─▶ M4 H HITL ─▶ M5 C 编排 ─▶ 收拢 I
                                                          └─────▶ M7 D 自进化（硬依赖：§5.4 裁决 + F 容器隔离先行）
             M6 E 渠道 + F 沙箱（可与 M3~M5 并行，社区可认领；F 相对 D 为硬前置）
```

## 7. 社区推进

- **现状（2026-10-15）**：仓库纯文档态——四份权威文档 + 兼容性三件套就位；LICENSE / CI / README / 官网随第一阶段落地（US-1 工程地基带出门禁与 CI，US-13 官网与 README，US-14 发布）。**缺口（尚无归属）**：`CONTRIBUTING.md`、issue / PR 模板、good-first-issue 运营——建议随 US-13 或社区期第一批补上。
- **低门槛贡献面**（需求文档 §7 口径：技能库与 MCP server 是最容易贡献的形态，不需要懂 Go）：
  - 技能投稿——一个 `SKILL.md` + 附属资源，零代码，按名被任意 Agent 绑定；
  - Agent 目录投稿——`AGENT.md` 即贡献（`examples/` 是可扩为投稿目录的雏形）；
  - MCP server——任意语言写一个 server（自研最小 server 是现成模板，脚本零第三方依赖）；
  - 新 Notify 适配器——写一个适配器 + 映射表一行（webhook / 飞书是样例）；
  - 新内置工具 / 新 Policy / Runner 实现——接口缝已留好，有契约测试钉子可依。
- **「五种人」定位映射**（沿 NivroOS 规划框架，按本仓实况标注）：

  | 面向谁 | 价值承诺 | 现状与阶段 |
  | --- | --- | --- |
  | 定义 Agent 的人 | 定义成本趋零（目录 + 一句话生成） | 第一阶段（US-12） |
  | 发布任务的人 | 从「用一个 Agent」到「指挥一群 Agent」 | 增量阶段（C / I） |
  | 运维 / 平台方 | 私有部署、数据不出域、成本可见、危险动作有人审批 | 部分（审计 / 沙箱 / 管理台随第一阶段）；H / G 补齐 |
  | 开发者社区 | 低门槛、新人友好 | 待补社区基建（本节） |
  | 行业 | 对接开放标准、不说私有方言 | MCP / OpenAI 兼容 / agentskills 形态已采纳；A2A 见 C |

- **协议开放**（需求文档 §7）：MCP（工具）、OpenAI 兼容（LLM）、agentskills.io 形态（技能）——不发明私有标准。

## 8. 风险清单

| 风险 | 症状 | 缓解 |
| --- | --- | --- |
| 单二进制纪律被新依赖破坏 | 向量 / 容器类依赖带 cgo → 交叉编译失败、静态断言红 | 新依赖先过 `CGO_ENABLED=0` 门（§5.1）；CI 四平台构建 + 静态性断言 |
| 版本坐标漂移 | 依赖随手升级，与实测锁定线脱节 | 引入前 goproxy.cn 实测核实；`go.mod` 变更走 `/us-register` 三问登记 |
| 安全面扩大 | `execute_code` / 自蒸馏 / 容器沙箱是新执行面与写入通道 | 设计先行 + HITL（§5.3 / §5.4） |
| 资源错配 | 单人节奏对标「九条并行」，每条都不闭环 | 按里程碑串行推进；低耦合面交给社区（§7） |
| 数据迁移 | SQLite → 外部存储无现成路径；`schema.sql` 非方言中立 | M3 内单独立项设计迁移与回滚；**不得**依赖自动 DDL（原则 9） |
| 范围蔓延 | G / I 体量大，容易吸走全部精力 | G 按信号切片；I 严格最后 |
| 文档不回写 | 权威文档与代码脱钩，下一次立项取到旧事实 | §4.3 回写表并入每 US 收尾；里程碑收口按表对账（可 grep 判） |
