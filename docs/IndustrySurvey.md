# Basalt 行业调研：Agent 底座的需求、生态与交付位置

本调研回答三个问题：为什么需要一个可控的 Agent 底座，现有方案各自交付什么，以及 Basalt 的选择是否值得验证。比较对象是实际部署形态、运行责任与故障行为，项目热度只说明关注度，不能证明可靠性或市场空白。

研究记录起于 2026-10-14；本轮于 **2026-10-18** 复核下文链接的官方仓库、文档与原始安全报告。项目能力按所查页面的声明描述，安全统计保留原报告观测日期；本轮未部署竞品做同负载测试。产品承诺见 [Requirements.md](Requirements.md)，实现选择见 [TechnicalDesign.md](TechnicalDesign.md)。

## 1. 先定义需要平台承担的责任

### 1.1 一个 Agent 从回答问题到执行任务，需要什么

一个可执行任务的 Agent 需要把模型、状态和外部动作连接起来。Basalt 将这条运行链路拆成五项基础责任：

| 基础责任 | 要解决的问题 | 典型失败 |
| --- | --- | --- |
| 模型接入 | 统一请求、响应、工具描述、错误与用量 | 错路由、协议字段丢失、取消未透传 |
| 推理循环 | 决定何时继续调工具、何时停止 | 无限循环、预算失效、半截工具消息 |
| 工具执行 | 接文件、进程、HTTP 与外部系统 | 副作用先于审计、子进程泄漏、错误被吞 |
| 上下文与记忆 | 管理会话、提示词快照及跨会话信息 | 串会话、旧配置混入运行、记忆越界 |
| 受控执行 | 将动作收敛到明确路径、命令和网络边界 | 白名单失效、凭证回显、把提示词当授权 |

这些责任构成本文所说的 **Agent runtime**：让一次任务能够受控推进并结束。只有模型 API 调用成功，尚不能证明整个任务可用；同样，工具很多也不代表失败时能恢复或解释结果。

### 1.2 runtime 与 Agent OS 的分工

当一个实例承载多个业务 Agent，还要解决资产管理、统一入口、触发与审计。这是 Basalt 使用“Agent OS”这个产品称呼的原因；此处是产品层次的类比，不是一个通用标准认证。

| 层次 | 管理单位 | 主要责任 |
| --- | --- | --- |
| 模型与协议层 | 一次模型或工具协议请求 | 编解码、连接和返回值 |
| Agent runtime | 一次 Run、一次会话与外部动作 | 循环、预算、工具准入、消息协议、终止和恢复 |
| Agent OS / 运行管理底座 | 多个 Agent 的资产与共享服务 | 目录装载、接入、记忆作用域、调度、配置与审计 |
| 企业治理与运维 | 用户、组织、环境与责任边界 | 身份、租户、审批、保留策略、隔离和发布运维 |

上层需要下层能力，但不能用名称推断已经交付。Basalt 核心阶段有运行和管理能力，认证、多租户、审批及强隔离仍按扩展边界推进，不能将“多个 Agent 共存”写成“多租户已隔离”。

### 1.3 比较时先问交付责任

| 决策问题 | 要看的实际证据 |
| --- | --- |
| 谁安装、升级和恢复底座 | 运行组件、工作区、备份与恢复步骤 |
| 谁决定一个外部动作能否发生 | 授权入口、文件 / 命令 / 网络边界 |
| 一次失败能否解释 | Run、模型、工具的关联记录与终态 |
| 中断后能否继续使用 | 会话协议、恢复可重入和不确定副作用处理 |
| 新业务任务怎样上线 | 声明校验、配置发布、工具接入和回滚路径 |

## 2. 从企业使用条件选择交付形态

### 2.1 相邻方案解决的是不同层次的问题

| 选择对象 | 通常交付的主要价值 | 与 Basalt 比较时核对什么 |
| --- | --- | --- |
| 模型客户端与协议 SDK | 请求编码、连接、工具 schema 和错误回传 | 是否持有工具执行权；谁维护运行状态与审计 |
| Agent 开发框架 | 用代码组合循环、状态、工作流和组件 | 能否嵌入既有系统；取消、权限与审计如何接线 |
| 工作流 / 应用平台 | 可视化配置、应用发布、插件和管理入口 | 目标任务需要固定流程还是自主工具循环；部署与治理成本 |
| Kubernetes 运行设施 | 工作负载生命周期、资源与隔离环境 | 是否已有集群；它管理工作负载还是也负责业务 Run |
| 云托管 Agent 服务 | 托管执行和配套服务 | 数据路径、地域、网络、身份及服务依赖是否满足部署要求 |
| 自托管助手或团队平台 | 会话、技能、工具、渠道与长期运行体验 | 具体部署档位、权限、审计、恢复和许可 |

类别之间可以组合。框架也可能附带部署能力，托管服务也可能提供私网选项，不能将所有项目简化成同一种能力边界；选型要比较对应版本与部署模式。

### 2.2 为什么企业需要私有、可控的运行底座

生产使用的难点已经包含质量与运行管理，而不只是模型接入。LangChain 于 **2026-06-12** 发布的调查覆盖 1,300 余名专业人士：质量是主要生产障碍，在较大企业样本中安全的重要性进一步上升；可观测建设也早于评测普及。这是供应商调查样本的观察，支持“可靠性值得投入”的判断，不等于所有企业的采购结论。[原始调查](https://www.langchain.com/state-of-agent-engineering)

Basalt 面向需要自己控制运行环境的组织，包括银行、政府、能源及有内网部署要求的业务团队。针对这一目标部署，提出三项必须逐客户确认的验收前提，而不是把它们概括成所有行业统一的法律规定：

| 使用前提 | 需要底座提供的具体能力 | 仍须部署方决定 |
| --- | --- | --- |
| 数据处理路径可控 | 工作区自托管，模型、MCP、HTTP、通知的出站路径明确 | 哪些数据可发给哪些服务，是否走私有模型或企业网关 |
| 动作可追溯 | 谁触发、何时调用、目标是什么、结果如何，能用关联标识查到 | 记录保留期、访问权限、备份与审计制度 |
| 工具权限可收敛 | 路径、可执行项与域名有明确准入，凭证不混入普通数据 | 信任哪些脚本与 Server，何时需要容器或更强隔离 |

这解释了“统一底座”的价值：业务团队复用同一套运行边界，新增 Agent 时不再复制模型接线、权限与审计机制。它是否能降低交付成本，要用上新时间、故障定位时间和实际运维投入验证。

### 2.3 长期价值包含可维护的知识资产

故障处理步骤、客户背景、项目约定和反复使用的操作方法，都可以沉淀为有作用域的记忆或可审阅的技能。价值主张是减少重复解释和经验丢失，同时让错误知识能够被纠正；不能仅以“自动化率”或生成内容数量判断收益。

记忆、技能和审计承担不同职责：记忆帮助后续任务取用背景，技能描述可复用的方法，审计解释已经发生的动作。三者都需要来源、权限与变更边界，保存更多内容本身不等于形成可靠知识库。

### 2.4 三种部署形态与真实数据边界

| 形态 | 适合的使用条件 | 需要承担的代价 |
| --- | --- | --- |
| 云托管 | 接受服务商的运行环境与数据处理路径，希望减少自运维 | 核对地域、网络、身份、费用和迁移条件 |
| 企业自托管 | 需要自己控制主机、工作区、凭证和运维，具备相应能力 | 安装、升级、备份、监控与暴露面由部署方负责 |
| 嵌入业务系统 | 已有应用希望直接接入运行能力 | 生命周期、升级和故障责任耦合；Basalt 尚未承诺通用嵌入式 SDK |

**自托管不等于数据不出网。** 云模型、远程 MCP、HTTP 工具和通知都可能发送数据；选择本地模型也不会自动关闭其他出站通道。Basalt 的定位是使这些边界明确并可验证，部署方仍须按实际拓扑配置。

## 3. 代表项目证明了什么，还需要比较什么

### 3.1 OpenClaw：助手体验与扩展生态同时放大收益和风险

OpenClaw 将助手、工具与扩展生态组合成可长期使用的产品，是研究低门槛任务接入的样本。当前官方仓库明确说明，同一 Gateway 可作为个人助手运行，也可配置为共享团队部署；因此不能沿用“只适合个人”的标签排除它，仍须比较实际治理与交付口径。[官方仓库](https://github.com/openclaw/openclaw)

安全案例提供了更具体的设计输入：

| 案例及原始日期 | 能支持的事实 | Basalt 应验证的对应行为 |
| --- | --- | --- |
| CVE-2026-25253；公告 2026-01-31，数据库于 02-02 更新 | `gatewayUrl` 被信任后可泄露网关令牌；受影响版本 ≤2026.1.28，2026.1.29 修复；CVSS 8.8 | 外部目标与凭证路径必须校验，日志和错误不得回显凭证；不能因仅监听 loopback 就推断安全 |
| ClawHavoc；Antiy CERT 2026-02-05 统计 | 在技能市场历史仓库中识别 1,184 个恶意 Skill 包；这是历史累计样本，不是当前在架数 | 技能来源可审阅；指令不能授权新增权限；脚本与 MCP Server 明确列入信任边界 |
| SecurityScorecard；报告署期 2026-02-09 | 原始页报告数以万计的互联网暴露部署，并说明测绘会动态更新 | 管理面、访问控制、凭证和部署配置需纳入验收；暴露不等于每台都已被入侵 |

来源分别为 [GitHub Advisory](https://github.com/advisories/GHSA-g8p2-7wf7-98mq)、[NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-25253)、[Antiy CERT 原始报告 §2.3](https://www.antiy.net/Download/clawhavoc-analysis-of-large-scale-poisoning-campaign-targeting-the-openclaw-skill-market-for-ai-agents.pdf) 与 [SecurityScorecard 原始研究](https://securityscorecard.com/blog/beyond-the-hype-moltbots-real-risk-is-exposed-infrastructure-not-ai-superintelligence/)。本轮复核日均为 2026-10-18，案例中的版本与观测日期不随复核日改写。

互联网暴露数量是动态测绘，IP、实例与可访问控制面的统计口径不同。原始页同时保留多个时点的计数，本调研使用可核对的暴露量级，不把单一精确数字当成当前存量；历史快照和当前能力应分开比较。

### 3.2 Hermes Agent：记忆与技能使长期使用成为产品能力

Hermes 的官方记忆文档说明了跨会话的有界记忆、用户信息、会话检索与技能沉淀；记忆会以快照形式进入后续上下文，并有按 profile 区分的使用边界。这表明长期使用体验需要专门的记忆模型，而不是只把历史消息无限追加。[官方记忆文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)

对 Basalt 的启发是把“下次任务是否确实少解释一次”写成验收：新会话是否加载记忆、作用域是否串用、修改何时生效、配额满时怎样失败。记忆存在不证明内容正确；错误信息的纠正和来源管理仍是产品问题。

### 3.3 企业使用留下的是一组需要证明的要求

两个样本展示了助手与学习体验，安全报告展示了权限和供应链风险。由此推导的机会不是“市场上没有企业平台”，而是：在客户可承受的部署成本下，将统一接入、作用域、受控动作、调用审计和可解释恢复组合成交付物。

这组要求与候选平台之间的差异，必须用同一套任务、配置和故障验收测量。未在本次材料中核实某功能，只能记“待验证”，不能写成对方没有；Basalt 也不能把计划中的治理能力当作现成优势。

### 3.4 Go 生态已有多个层次

以下分类依据 2026-10-18 所查官方仓库的用途说明，不是性能、成熟度或市场份额排名：

| 层次 | 官方项目与用途 | 对 Basalt 选型的含义 |
| --- | --- | --- |
| 应用 / Agent 框架 | [eino](https://github.com/cloudwego/eino)、[langchaingo](https://github.com/tmc/langchaingo)、[adk-go](https://github.com/google/adk-go)、[trpc-agent-go](https://github.com/trpc-group/trpc-agent-go)：组件、Agent 或工作流开发 | Go 已有完整的应用开发选择；本仓自持循环是为了直接约束执行语义，不是因为没有框架 |
| 集群运行与隔离 | [kagent](https://github.com/kagent-dev/kagent)、[agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)：云原生 Agent 与隔离工作负载 | 已有 Kubernetes 的团队应评估原生方案；单机部署也应明确自己的资源隔离边界 |
| 助手与团队协作 | [PicoClaw](https://github.com/sipeed/picoclaw)、[GoClaw](https://github.com/nextlevelbuilder/goclaw)、[AgentTeams](https://github.com/agentscope-ai/AgentTeams)：轻量助手、团队平台或经 Matrix 协作 | 比较实际使用者、依赖、许可、资产协议和治理组合，不能声称 Go runtime 空白 |
| 工具协议 | [官方 go-sdk](https://github.com/modelcontextprotocol/go-sdk)、[mcp-go](https://github.com/mark3labs/mcp-go)：MCP 客户端 / 服务端 | 可复用工具生态，仍需自己定义注册、授权、审计及资源生命周期 |

### 3.5 PicoClaw / GoClaw 要按部署档位比较

| 比较项 | PicoClaw | GoClaw Lite | GoClaw Standard | Basalt 核心阶段设计 |
| --- | --- | --- | --- | --- |
| 官方定位 / 档位 | 轻量 Go 助手 | Desktop / Lite | Server / Standard | 企业自托管运行底座 |
| 状态与运行依赖 | 官方强调轻量部署；具体后端以所用版本为准 | 本地 SQLite | PostgreSQL；语义记忆用 pgvector | 单二进制 + 嵌入式 SQLite，底座不要求外部数据库 / 缓存 / 队列 |
| 团队与治理 | 按版本核对 | 官方比较表限制 Agent / 团队规模，无 Standard 的 RBAC / 多租户项 | 官方比较表声明 RBAC / 多租户 | 核心阶段无认证 / 多租户，不以“企业”名称冒充已经具备 |
| 许可核对 | MIT | GoClaw 仓库 main 的 LICENSE 为 CC BY-NC 4.0 | 同左 | 以本仓实际许可文件及发布决定为准 |
| 应重点实测 | 长期运行、权限、会话与工具行为 | 与本仓单机形态的实际差异 | 现成治理能力与额外运维组件的权衡 | 审计预写、路径 / 命令 / 域名准入、目录配置与恢复语义 |

核对入口：[PicoClaw 仓库](https://github.com/sipeed/picoclaw)、[GoClaw Lite / Standard 对照](https://github.com/nextlevelbuilder/goclaw#lite-vs-standard)、[GoClaw LICENSE](https://github.com/nextlevelbuilder/goclaw/blob/main/LICENSE)（2026-10-18）。许可表仅记录文件标识；引入代码或商业部署时按所用版本核对授权条件，不能仅凭仓库公开或 GitHub 元数据推断可用范围。

SQLite Lite 的存在意味着“没有外部数据库”不能单独构成 Basalt 的差异。Basalt 要证明的是部署、权限、审计、资产与恢复这组行为是否共同满足目标场景；本轮尚未完成竞品同口径实测。

### 3.6 Go 作为底座语言的六个工程支点

| 工程支点 | 在 Basalt 中解决什么 | 代价或验证要求 |
| --- | --- | --- |
| 编译为发布制品 | 一个版本对应一个可校验的执行文件 | CGO=0 与依赖兼容性必须逐构建验证 |
| 并发与取消原语 | 处理 I/O、超时、请求结束与资源清理 | goroutine 不自动消亡，race 全绿也不证明所有时序正确 |
| 标准网络与进程库 | 保持 HTTP、context、进程执行与信号控制的接口可见 | 进程树和网络边界需分平台实测 |
| 显式类型与小接口 | 分离 core、适配器、Policy 与 Runner | 仍需约束依赖方向和唯一执行入口 |
| 原生测试、竞态与基准工具 | 快速反馈、并发问题定位和性能测量 | 先设计失败模式，覆盖率只是底线 |
| 交叉构建与资源嵌入 | 交付多平台制品和时区等运行资源 | 交叉编译成功不等于对应平台已启动验收 |

这些是工程适配理由，不是“Go 比其他语言快或更安全”的结论。语言机制与可移植性参考 [Go 官方 FAQ](https://go.dev/doc/faq)，本仓构建与运行证据另见技术方案和 CI；没有同负载实验时不作跨语言性能排名。

MCP 已有官方 Go 客户端 / 服务端 SDK，使工具连接不必从头自造协议。但 SDK 的存在不代替注册顺序、分页、凭证、取消、审计和子进程寿命的工程工作；本仓以锁定版本和 US 专属回归定义这些边界。

## 4. Basalt 的定位、边界与可验证选择

### 4.1 定位落在四个交付结果

| 定位 | 用户应得到什么 | 不能用来替代的承诺 |
| --- | --- | --- |
| 统一 | 多个业务 Agent 复用运行入口、工具、记忆与审计机制 | 不等于业务流程都由底座编排 |
| 私有 | 实例资产和数据由部署方控制，出站路径显式配置 | 不等于默认断网或所有模型都在内网 |
| 易接入 | 目录声明、REST、技能与 MCP 接入有清晰契约 | 不等于第三方代码无需审核或依赖为零 |
| 可观测 | 能关联一次 Run 的模型 / 工具调用与失败结果 | 不等于已具备所有企业治理能力 |

核心阶段交付运行控制、会话与长期记忆、受控工具、接入和调度，以及已经规划的管理与展示面。认证、租户、审批、强隔离、语义记忆和分布式能力按各自扩展 US 验证；本调研不扩大 [需求范围](Requirements.md#release-scope)。

### 4.2 从公开风险反推 day-one 设计

| 风险教训 | 本仓对策 | 专属 Harness 的判据方向 |
| --- | --- | --- |
| 外部地址或错误正文携带凭证 | 配置解析、凭证占位与对外错误脱敏 | 拒绝错误目标；日志 / 响应 / 错误不含秘密 |
| 动作权限被指令或插件放大 | Policy / Runner 分离、白名单、来源审核 | 越界请求在发送或执行前拒绝，外部动作零次 |
| 工具做了事但没有证据 | 调用前 pending 审计，失败关闭 | 审计预写失败不得调用；终态失败保留不确定状态 |
| 长期使用积累错误状态 | 作用域、配额、快照和恢复契约 | 跨 Agent 不串用，运行内不混版本，恢复可重入 |
| 演示通过掩盖故障 | 失败模式、逆改、整链路与故障注入 | 检查动作集合 / 内容 / 时序 / 状态，不以测试条数代替 |

这些对策是 Basalt 自身的设计要求，不能因写进文档就称已完成；产品范围和每次验收读数分别登记。白名单与审计也不能约束受信 MCP Server 内部的一切行为，强隔离仍需独立执行环境。

### 4.3 选择的收益与成本同时验证

| 设计选择 | 预期收益 | 代价与必须验证的事项 |
| --- | --- | --- |
| Go 单二进制与 SQLite | 减少底座运行组件，便于安装、备份与恢复 | 依赖兼容、并发写、制品体积和运行资源分别测量 |
| 自持 Run 与工具执行入口 | 明确取消、预算、审计顺序和失败归属 | 自己维护协议与恢复回归，避免形成新的隐式框架 |
| 目录声明与加载期校验 | 任务资产可审阅、版本化和低代码上线 | 管理写入、快照、热加载与失败语义必须一致 |
| 协议 SDK / MCP | 复用外部生态，保持连接与调度职责清楚 | 升级要复验分页、上下文、握手和进程寿命 |

与业界项目的关系是按目标环境取舍、按协议互通、按同一故障样本比较。框架可以是研究对象，Kubernetes 平台可以是另一种交付方案，助手项目可以提供体验样本；它们都不是 Basalt 成立或优越的自动证明。

## 5. 如何证明项目值得继续投入

| 验证题 | Basalt 的证据挂点 | 何时需要重新评估 |
| --- | --- | --- |
| 固定任务能否稳定完成且不越权 | behavior / injection 固定用例、工具审计 | 模型、工具、协议或权限边界变化 |
| 多入口是否承诺相同行为 | CLI / HTTP / 调度共用 Run 与故障回归 | 增加入口、调度规则或会话操作 |
| 取消和崩溃后能否继续使用会话 | 进程树测试、消息组补齐与恢复可重入 | 存储、Runner 或恢复顺序变化 |
| 长期使用是否减少重复说明 | 新会话的记忆验证、D4 风险基线 | 作用域、配额、检索或载体变化 |
| 新工具能否以明确边界接入 | MCP 子进程协议测试、D5 只读资料场景 | SDK、Server 配置或传输方式变化 |
| 开发过程能否发现错误实现 | 任务反例、统一验收 JSON、Loop 最终断言并集 | 判据、配置或被验证源码变化 |

固定替身评测证明预设链路满足断言，不能替代真实模型能力评测或开放世界抗注入结论。D1–D5 是业务验收目标，未交付的样例不作为当前证据。性能目标同样需要环境、负载与测量记录。

如果实际部署仍需要大量未登记的组件、失败无法追溯、权限边界只能靠指令维持，或恢复会重复外部动作，就应修订设计或缩小范围；不能用覆盖率、项目数量或演示措辞掩盖问题。

## 6. 扩展投入的触发条件

| 出现的具体信号 | 才进入评估的能力 | 前置验证 |
| --- | --- | --- |
| 单实例写入或并发达到可测瓶颈 | 外部状态、排队与分布式调度 | 事务语义、幂等边界、迁移与故障恢复 |

### 7.1 论证与证据如何对应

调研需要同时解释责任分层、企业需求、代表项目、安全案例、生态与产品定位。证据纪律限定结论的适用范围，不能代替回答“为什么值得做”；候选链接、调查方法和实际选型理由分别呈现。

- 官方 README / 文档支持项目自述和部署模式；本轮查询基于所查页面，不冒充固定 commit 的竞品实测。
- 安全公告支持特定版本的漏洞事实，研究统计支持其观测窗口；不能推出平台所有版本均不安全。
- 行业调查支持其样本中的趋势，不能替代目标客户需求访谈、采购约束和实际部署验证。
- Basalt 的收益、差异与成本是验证假设，须用任务结果、安装前置、故障证据和维护投入检验。
- 新的量化研究记录注明日期、版本 / commit、模式、方法和原始来源；旧稿热度快照留在 Git 历史，不补造最新数字。

项目历史、跨项目迁移和兼容对照集中在 [Compatibility.md](Compatibility.md)。外部事实引用保留来源，本仓是否已实现仍由模块记录和运行证据决定。

<a id="survey-terms"></a>

### 7.2 阅读运行设计所需的对象

| 术语 | 定义 |
| --- | --- |
| **Agent（智能体）** | 一个具象的业务智能体，定义本体是一个目录 `.basalt/agents/<name>/`：`AGENT.md`（frontmatter 是运行配置、正文是任务指令）加可选 `scripts/`、`REFERENCE.md`。一个目录就是一个完整可用的业务 Agent |
| **Profile（配置）** | 底座内部的运行时配置对象，由 `AGENT.md` 的 frontmatter 派生（`deriveProfile`），决定这个 Agent 用什么 Provider、可用哪些 Tool、绑定哪些 Skill、有没有定时 |
| **Provider（供应商）** | LLM API 服务的抽象。Basalt 通过 OpenAI 兼容协议对接各家（DeepSeek/通义/Kimi/智谱/本地 vLLM 等），维护显式的 provider name → 客户端映射 |
| **ReAct 循环** | Agent 的核心工作机制：Reason + Act。模型思考是否调工具、调用后看结果、再决定下一步，直到给出最终响应 |
| **Tool（工具）** | Agent 可调用的外部能力。内置工具（文件/命令/HTTP/记忆/通知）+ Plugin 三档扩展（Agent 目录加 MCP / 自写 MCP server / 在 Basalt 代码内实现接口） |
| **Memory（记忆）** | Agent 跨对话保留的状态。核心阶段两层：会话记忆（SQLite 持久化）与长期记忆（`MEMORY.md` 与 `memory_entries` 表，按 Agent 分层 + 全局回退层） |
| **Skill（技能）** | 公共实体存 `.basalt/skills/<name>/SKILL.md`；Agent 在 `AGENT.md` frontmatter 的 `skills:` 里**声明式绑定**（声明即绑定，各平台一致）。每轮只注入 name/description/路径（L1），模型按需 `read_file` 读正文（L2）、取附属资源（L3）。Skill 不是 Tool，不进工具注册表 |
| **Channel（渠道）** | Agent 对外的消息入口。核心阶段内置 CLI；IM 渠道在扩展阶段 |
| **Session（会话）** | 用户与 Agent 一次对话的上下文容器，按 channel+user+profile 联合标识，持久化到 SQLite |
| **Sandbox（沙箱）** | 工具执行的受控边界，拆成授权与执行两个接口：`Policy.Check`（能不能做）+ `CommandRunner.Run`（怎么做）。核心阶段唯一组合 = `WhitelistPolicy`（应用层白名单：路径/命令/域名）+ `LocalRunner`（进程内本地执行） |
| **Bootstrap（引导文件）** | 注入系统提示词的上下文文件：`AGENTS.md`（项目级行为说明）、`SOUL.md`（人格）、`USER.md`（用户偏好，只读不写） |
| **Workspace（工作区）** | Basalt 实例的工作目录 `.basalt/`，包含 Agent 目录、技能库、记忆、配置、日志与 SQLite 数据库 |
| **MCP** | Model Context Protocol，Agent 工具接入的开放标准；Basalt 作 Client 连接外部 MCP server |
