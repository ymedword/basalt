## User Scenarios & Testing *(mandatory)*

**标签口径（`[US1]`~`[US4]` 不混淆）**：下面四个用户故事在 `tasks.md` 中以 Spec-Kit 的工具标签 `[US1]`~`[US4]` 出现——那是**本 feature 内部**用户故事的编号，**不是**项目台账（[docs/us/REGISTRY.md](../../docs/us/REGISTRY.md)）里的 US-1 ~ US-8。本 feature 的四个故事同属项目 **US-8（通知工具）** 一个模块，是它的四个独立可验场景；标签按工具产出保留。

### User Story 1 - 登记渠道后一次推送闭环（Priority: P1）

运维在渠道注册表里登记一个渠道（例如飞书机器人，`url` 列值为 `${BASALT_NOTIFY_OPS}`，真实地址放在进程环境）。Agent 在巡检后调用 `notify`，给出 `channel: ops` 与一段 `content`。消息真实送达接收端；工具结果是固定文案 `已推送到通知渠道：ops`；模型据此知道"已推送、推到哪"。这是本模块的验收 Demo（真 webhook 发一条，凭证由人工在执行时输入）。

**Why this priority**: 它是本模块的旗舰路径与全部价值的前提——没有"选对渠道并把内容发出去"，其余故事（脱敏、判定、审计）都无从谈起。放 P1 还因为它是唯一的正向链路：这条不对，通知能力对 Agent 完全不可见。

**Independent Test**: 以进程内假发送端 + 假策略驱动工具与执行器：给定一条已登记的渠道与一条调用（`channel` 命中、`content` 非空），断言 ①策略判定通过后发送端恰好收到一次调用、收到解析后的真实地址与原文内容；②工具结果为固定成功文案且不可重试标记为否；③审计行经历 `pending → 成功` 两阶段。全程不访问真实网络。

**Acceptance Scenarios**:

1. **Given** 注册表有一条名为 `ops` 的渠道且其引用变量已设置，**When** Agent 调用 `notify`（`channel: ops`、`content: 巡检摘要`），**Then** 发送端收到一次投递、内容与入参逐字一致，工具返回 `已推送到通知渠道：ops`。
2. **Given** 同一次调用，**When** 查看审计记录，**Then** 调用发生前已有 `pending` 行、返回后同一行回填终态；工具与发送端本身不产生第二行审计、不写消息、不记日志。
3. **Given** 注册表为空或渠道名写错，**When** 调用 `notify`，**Then** 调用失败（`not_found`）并列出当前可用渠道名，发送端零调用。

### User Story 2 - 无默认渠道、失败可诊断（Priority: P2）

模型忘记传 `channel`、传了纯空白，或把渠道名写错时，系统**不猜默认渠道**：调用失败，错误文本列出当前可用渠道名，模型可据此自我纠正。`content` 超过 20 KiB 的调用在读取注册表**之前**即失败；空串 `content` 放行（接收端可自行拒绝）。每次发送都重新读取注册表，管理端改动渠道行后下一发即生效、无需重启。

**Why this priority**: "静默发到错误目标"是多渠道实例最危险的默认行为；可诊断的失败让模型能自愈，也让运维能从错误文案定位问题。放 P2 是因为它守住 P1 的可用性，而非新增正向能力。

**Independent Test**: 以可计数的假注册表与假发送端驱动工具：①`channel` 缺失 / 纯空白 / 查无 → `not_found`、文案含可用渠道名（空表时说明注册表为空）、发送零次；②`content` 恰好 20 KiB 放行、超 1 字节失败、中文按 UTF-8 字节计、超限时注册表读取次数为 0；③空串 `content` 照常发送一次；④连续两次发送 → 注册表读取两次；构造工具后新增渠道行可见。

**Acceptance Scenarios**:

1. **Given** 注册表有 `ops` 与 `dev` 两条渠道，**When** 调用不传 `channel` 或传空串 / 纯空白，**Then** 失败（`not_found`）且错误文本含 `ops` 与 `dev`，发送零次。
2. **Given** 调用传 `channel: ghost`，**When** 执行，**Then** 失败（`not_found`）且错误文本点名 `ghost` 并列出可用渠道名，发送零次。
3. **Given** `content` 为 20 KiB + 1 字节，**When** 执行，**Then** 失败（`invalid_input`）且注册表读取次数为 0、发送零次；**Given** 恰好 20 KiB 或空串，**Then** 放行并发送一次。
4. **Given** 工具已构造，**When** 注册表新增一行后再次发送，**Then** 新渠道可见；两次发送共读取注册表两次（无缓存）。

### User Story 3 - 凭证红线与判定边界（Priority: P3）

渠道地址里的 path / query / userinfo 就是 token。系统在三个层面守住它：①注册表的 `url` 列**只允许精确 `${VAR}` 引用**，明文或半截占位一律拒绝且错误不回显地址；②引用只在**发送那一刻**经进程环境解析，未设置或为空串即失败关闭，错误只点名变量名、不回显值；③发送前必须经统一策略判定，判定对象是**解析后的真实地址**，判定通过之前发送端一次都不得被调用。策略拒绝若为沙箱越界，保留规则与指引原文、把目标重写为 `scheme://host`；传输失败文案只用固定类别短语 + `scheme://host`，原始错误只进原因链。工具与发送端不持有 logger。

**Why this priority**: 这些都是"错了不立刻显形"的安全面——明文地址要到日志外泄才被发现，先发后判要到越界请求产生副作用才被发现，文案透传要到 token 进入模型上下文才被发现。放 P3 是因为它守住 P1 / P2 的边界而非新增功能。

**Independent Test**: ①明文地址 / `${A}${B}` / `${A}x` / `$A` / `${}` / `${1A}` → 失败且文案不含地址；②变量未设置 / 空串 → 失败且只点名 `${VAR}`；③假策略故意在拒绝文案的段 2 嵌完整 URL → 工具输出只含 `scheme://host`，规则与指引原文保留；④策略判定一次、发送零次（拒绝路径）；⑤发送端传输错误含哨兵 token → 工具输出与错误文案零命中。

**Acceptance Scenarios**:

1. **Given** 某渠道 `url` 是明文地址，**When** 发送，**Then** 失败（`runtime_error`），错误点名渠道与"必须是 `${VAR}` 占位"，且不包含该地址任何片段。
2. **Given** 某渠道 `url` 是 `${MISSING_VAR}` 且变量未设置或为空串，**When** 发送，**Then** 失败（`runtime_error`），错误点名 `MISSING_VAR`，不含环境值，发送零次。
3. **Given** 真实地址不在域名白名单内（策略拒绝），**When** 发送，**Then** 失败（`sandbox_denied`），四段式文案的段 2 只有 `scheme://host`（无端口 / userinfo / path / query），判定一次、发送零次。
4. **Given** 发送端返回含完整地址的传输错误，**When** 工具返回，**Then** 可观察文案只有固定类别短语 + `scheme://host`，原始错误不出现在结果 / 日志 / 审计任何一处。

### User Story 4 - 投递真值与同形装配（Priority: P4）

成功不等于 HTTP 2xx。`webhook` 的成功判据是 2xx（仅表示自定义接收端 / 中转服务接受了请求，不承诺业务级投递成功）；`feishu` 的成功判据是 2xx **且**响应体 `code == 0`——飞书业务失败同样回 HTTP 200，回执不可解析（空体 / 非 JSON / 缺 `code` / `code:null` / 小数 / 尾随垃圾）或超过 64 KiB 一律判失败，不把"结果未知"冒充成功。两个发送端都不跟随重定向、不读环境代理；取消 / 截止的身份优先于外部错误（执行器归 `timeout`）。`notify` 以第 9 件内置工具的身份装配：注册顺序为 notify → 等值门禁 → MCP，声明名集九名，轻路径与重路径结论一致。

**Why this priority**: 这些是"实现错了不一定立刻红"的判别力面——2xx 误判成功、截断回执误判成功、重定向绕过白名单、审计缺行，都要靠专门用例钉住。放 P4 是因为它们收敛 P1~P3 的行为，而非新增用户可见能力。

**Independent Test**: ①webhook 收到固定载荷、2xx 成功、4xx/5xx/3xx 失败且响应体关闭；②feishu 固定载荷、`code=0` 成功、`code=19024` 失败且文案含 code 不含回执正文、回执矩阵逐档失败；③有效 `{"code":0}` + 超限空白 → 失败（防截断误绿）；④真实回环单跳重定向：第二跳零发生；⑤适配器实际持有的客户端不读环境代理；⑥ctx 取消 / 截止 → 返回裸哨兵；⑦装配后工具清单恰好九件且含 `notify`，映射恰好 `webhook` / `feishu` 两键，轻路径接受声明 `notify` 的 Agent。

**Acceptance Scenarios**:

1. **Given** feishu 接收端返回 HTTP 200 且 `code=19024`，**When** 发送，**Then** 工具失败（`external_error`），审计 `error_kind=external_error`，文案含 `code=19024` 且不含回执正文。
2. **Given** feishu 接收端返回 HTTP 200 且回执为空 / 非 JSON / `code:null` / 小数 / 尾随垃圾 / 超过 64 KiB，**When** 发送，**Then** 一律失败（`external_error`，固定「飞书回执无法解析」文案）；**Given** `code=0`，**Then** 成功。
3. **Given** webhook 接收端返回 302 指向另一地址，**When** 发送，**Then** 不跟随重定向、判定失败（`external_error`），第二跳零请求。
4. **Given** 装配完成，**When** 查看工具清单与声明名集，**Then** 恰好九件且含 `notify`，类型映射恰好 `webhook` / `feishu`，声明 `notify` 的 Agent 在轻路径与重路径均被接受。

### Edge Cases

- **空 `content`**：放行并发送一次（人工 review ① 裁决 A；接收端可自行拒绝）。
- **`content` 缺失**：由执行器的 schema 必填校验在工具调用之前拦截（工具不会被调用）。
- **`content` 为 `null` / 非字符串**：失败（`invalid_input`），零外呼。
- **`content` 边界**：UTF-8 字节恰好 20 KiB 放行、超 1 字节失败；中文按 3 字节 / 字符计。
- **`channel` 缺失 / 空串 / 纯空白**：视同"未指定"，失败（`not_found`），列出可用渠道名。
- **注册表为空**：错误说明注册表为空，不猜默认渠道。
- **注册表读取失败**：失败（`runtime_error`）；若 ctx 已取消 / 截止，返回 ctx 哨兵（`timeout`）。
- **渠道 `type` 未装配**：专用错误（`runtime_error`），不查环境、不调策略、不发送。
- **`url` 非精确 `${VAR}`**：失败（`runtime_error`），不回显地址；`${A}${B}` / `${A}x` / `$A` / `${}` / `${1A}` / `${A-B}` 全部拒绝。
- **环境变量未设置 / 空串**：失败（`runtime_error`），点名变量名，不回显值，不把引用串当 URL 发送。
- **解析后的环境值不构成合法 URL / scheme 非 http(s) / host 为空 / IP 字面量 / 非默认端口**：不新增 URL 预检，由既有策略判定拒绝（`sandbox_denied`，段 2 为 `scheme://host` 或「目标无法解析」占位），发送零次。
- **feishu 回执携带其他字段**：`StatusCode` / `msg` / `data` 等额外字段不影响判定；JSON 值之后的空白不算尾随垃圾，非空白字节才算。
- **webhook 2xx**：成功，不读取响应体；**3xx / 4xx / 5xx**：失败（`external_error`），文案只含状态码 + `scheme://host`。
- **feishu 2xx 但回执 `code != 0`**：失败（`external_error`），文案含 `code=<N>`、不含回执正文。
- **feishu 回执不可解析 / 超限**：失败（`external_error`），固定「飞书回执无法解析」文案。
- **重定向**：不跟随；3xx 按失败处理，不产生第二跳请求。
- **环境代理**：不读取；设置 `HTTP_PROXY` 不改变出口。
- **ctx 取消 / 截止**：发送与回执读取两处都优先返回裸哨兵，执行器归 `timeout`。
- **并发调用**：注册表只读、工具无共享可变状态，`-race` 无告警。
- **渠道行新增**：工具构造后新增的行在下一发可见（每次读表、无缓存）。
- **`description` / `created_at`**：本 US 不读，不参与任何判定。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 工具名 MUST 固定为 `notify`；入参 schema 中 `channel` 可选、`content` 必填；缺失 `content` 由执行器的 schema 必填校验在调用工具之前拦截。
- **FR-002**: 系统 MUST NOT 设有默认渠道；`channel` 缺失、纯空白或查无时调用失败（`not_found`），错误文本列出当前可用渠道名。渠道名 MUST 在去除首尾空白后按大小写敏感精确匹配，不做前缀 / 模糊匹配。
- **FR-003**: `content` 按 UTF-8 字节计 MUST NOT 超过 20 KiB；超限在读注册表之前失败（`invalid_input`）；空串放行。
- **FR-004**: 工具 MUST 每次发送读取一次渠道注册表、不缓存，并按渠道名稳定升序返回；构造后新增的行可见。
- **FR-005**: 渠道地址 MUST 是精确 `${VAR}` 引用（`${` + 标识符 + `}`；标识符 = `[A-Za-z_][A-Za-z0-9_]*`，即字母或下划线开头，其后可含字母、数字、下划线）；明文、`${A}${B}`、`${A}x`、`$A`、`${}`、`${1A}` 等一律拒绝，错误文本不回显地址。
- **FR-006**: 引用 MUST 只在发送时经进程环境解析；未设置或值为空串一律失败关闭，错误点名变量名、不回显环境值、不得把引用串当 URL 发送。
- **FR-007**: 类型 → 发送适配器的映射 MUST 只存在于装配层，恰好 `webhook` / `feishu` 两键；工具内核只按渠道类型查表，MUST NOT 出现类型判断分支。
- **FR-008**: 未知类型 MUST 返回专用错误（归 `runtime_error`），且不查环境、不调策略判定、不发送。
- **FR-009**: 发送前 MUST 经统一策略判定：判定对象是解析后的真实 URL，Agent 名为显式值传导，动作类型固定为 HTTP 请求。
- **FR-010**: 策略判定通过之前，发送适配器 MUST NOT 被调用一次。
- **FR-011**: 策略拒绝为沙箱越界时，系统 MUST 保留规则与指引原文、把目标重写为 `scheme://host`（解析不出用既有「目标无法解析」占位）；MUST NOT 透传嵌着完整 URL 的越界值。
- **FR-012**: 渠道地址（含端口 / userinfo / path / query）MUST NOT 出现在任何模型可见结果、日志、审计或错误文案；对外只出 `scheme://host`。工具与适配器 MUST NOT 持有 logger。
- **FR-013**: `webhook` 适配器 MUST 发送固定载荷 `{"content": "…"}`；成功判据 = HTTP 2xx（仅表示接收端接受请求，不承诺业务级投递成功）；3xx / 4xx / 5xx 一律失败（`external_error`），文案只含状态码 + `scheme://host`；所有响应分支都关闭响应体，2xx 成功体不读取。它只面向接受 Basalt JSON 协议的自定义接收端 / 中转服务，MUST NOT 承诺原生企微 / 钉钉直连。
- **FR-014**: `feishu` 适配器 MUST 发送固定载荷 `{"msg_type":"text","content":{"text":"…"}}`；成功判据 = HTTP 2xx 且响应体 `code == 0`（JSON 整数）；`code` 非 0 → 失败（`external_error`），文案含 `code=<N>` 但不含回执正文。
- **FR-015**: 飞书回执不可解析 MUST 判失败（`external_error`，固定「飞书回执无法解析」文案）：空体、非 JSON、缺 `code`、`code` 为 `null`、`code` 非整数（含小数）、JSON 之后有非空白尾随字节。回执允许携带其他字段（`StatusCode` / `msg` / `data` 等），只以 `code` 为判据。
- **FR-016**: 飞书回执最多读 64 KiB；超限 MUST 按"无法解析"判失败，并 MUST 显式检测超限（多读 1 字节或以 `LimitReader(max+1)` 判断长度），MUST NOT 读满上限后截断解析。
- **FR-017**: 两个适配器 MUST NOT 跟随重定向、MUST NOT 读取环境代理（沿用既有 HTTP 客户端配置）；3xx 原样交回判定并计为失败。
- **FR-018**: DNS / TLS / 连接失败的文案 MUST 只用固定类别短语 + `scheme://host`；原始错误只进原因链，MUST NOT 渲染。
- **FR-019**: 适配器在包装发送错误与回执读取错误之前 MUST 先判 ctx；取消 / 截止命中即返回裸哨兵（执行器归 `timeout`），MUST NOT 包成外部系统错误。
- **FR-020**: 工具与两个适配器 MUST 保持静默：不落审计、不写消息、不记日志；审计行与失败 WARN 由既有工具执行器统一承担。
- **FR-021**: 调用 MUST 经既有工具执行器两阶段审计：调用前 `pending` 行必须已落库（预写失败即拒绝发出）；返回后同一行回填终态；失败由执行器记 WARN 并把错误文本回填为工具结果。
- **FR-022**: 成功返回 MUST 固定为 `已推送到通知渠道：<渠道名>`，不可重试标记为否。
- **FR-023**: `notify` MUST 是第 9 件内置工具，注册顺序固定为 notify → 等值门禁 → MCP（notify 在注册池等值门禁之前，MCP 工具在门禁之后）；声明名集同步为九名（排序），轻路径与重路径共用同一份声明。
- **FR-024**: 范围 MUST 零膨胀：零迁移（渠道表自初始 schema 已存在）、零新增配置键、配置文件与依赖清单零 diff；本 US 对注册表只读，渠道增删改查归后续 US。

### Key Entities

- **通知渠道行**：全局注册表的一行，工具只消费 `name`（渠道名、精确匹配键）、`type`（适配器映射键）、`url`（`${VAR}` 引用）；`description` 与 `created_at` 本 US 不读。发送路径只读，写入归后续 US。
- **环境变量引用**：形如 `${VAR}` 的整串引用；发送时解析为真实地址；真实地址不对任何可观察面暴露。
- **工具调用审计行**（既有）：`pending → 终态` 两阶段；`error_kind` 取既有七值；本 US 不新增表、列或写入点。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 已登记渠道的一次调用在接收端真实送达，工具结果为固定成功文案，成功率 100%（测试夹具与验收 Demo 各一次）。
- **SC-002**: 在任何可观察面（工具结果 / 日志 / 审计错误文本 / 终端输出）中，真实渠道地址的完整形态（端口 / userinfo / path / query / token）出现次数为 **0**；只允许 `scheme://host`。
- **SC-003**: 飞书 HTTP 200 但业务回执 `code != 0` 的调用，100% 被判为失败（`external_error`），零误判成功。
- **SC-004**: 所有"发送前失败"的路径（无渠道 / 名字查无 / 内容超限 / 占位非法 / 环境变量缺失 / 策略拒绝 / 未知类型 / 注册表读取失败）外呼次数为 **0**。
- **SC-005**: 管理端修改或新增渠道行后，下一发即生效（无需重启）；同一工具实例连续两次发送读取注册表 **2** 次（无缓存）。
- **SC-006**: webhook 的 3xx / 4xx / 5xx 与网络传输失败，100% 被判为失败（`external_error`）；重定向目标请求次数为 **0**。
- **SC-007**: 装配完成后工具清单恰好 **9** 件且含 `notify`，类型映射恰好 **2** 键；轻路径与重路径对同一份 `AGENT.md` 声明给出一致结论。

## Assumptions

- 运维在演示前手工向渠道注册表登记渠道行（本 US 不含 CRUD）；渠道行由后续 US 提供管理面。
- 渠道的真实地址放在进程环境变量中，变量名由运维登记行时决定；进程环境在启动时固定，改值需重启生效。
- 飞书群机器人 webhook 的文本协议为：正确载荷回 HTTP 200 且响应体 `code=0`；错误（含关键词不匹配）同样回 HTTP 200 但 `code != 0`。
- 依赖 US-4 已交付的工具接口、工具执行器、注册池、失败分类与统一策略接口；US-1 的渠道表与仓储形态、US-6 的装配接线、US-7 确立的门禁位置均复用。
- 不自动重试、无恰好一次承诺；重试与幂等键属扩展阶段。
- 真实外呼与凭证相关人工项（真 webhook、飞书错关键词、凭证面 grep、手工登记渠道等）按颗粒度文档 §6.1 在实现完成后由用户执行；自动化层通过不替代这些人工项。
