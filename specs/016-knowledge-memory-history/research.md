## R-01 PostgreSQL 与 pgvector 版本（D-04）

- **Decision**: 目标 PostgreSQL **16/17**，`vector` 扩展 **0.8.x**，`pg_trgm` 用于中文关键词路径基线；CI 使用明确标记的固定候选镜像。
- **Rationale**: 向量检索与触发器索引需要在同一引擎内完成；与 SQLite 的迁移切割点一致。
- **实测（2026-10-27，`dev-env/evidence/postgres-windows.json`）**: PostgreSQL **17.11**、`vector` **0.8.7**、`pg_trgm` **1.6**；非超级用户建表、精确余弦检索、HNSW + 迭代扫描、事务回滚、schema 清理、强制口令认证七项全部为真。
- **契约落地复测（2026-10-28，`dev-env/evidence/pg-schema-contract-check.json`）**: `docs/contracts/schema.pg.sql` 全文（1185 行，B-01 裁决后重冻结版）在目标引擎连跑两遍幂等，建出 **52 表**，`kb_chunk_embeddings.embedding` 为 `vector(512)`，ANN 索引数 **0**，时间列全部 `bigint` 毫秒（`timestamptz` 列数 **0**），8 条负向约束全部拒绝坏写入，存量迁移 Run（`admin-builtin` + `local-admin`）可写入；本轮以**非超级用户** `basalt_test` 执行，覆盖首轮「未用非超级用户跑这 52 表 DDL」的缺口。**未覆盖**：任何查询性能、`CREATE INDEX` 实测。
- **R18 重冻结复测（2026-10-28）**：契约改 1191 行 / `d9e72c8a…`（`purpose` 增 `retrieval` 与 `compaction`；`compaction_entries` 消息标识列改 `text`、去外键与列间顺序 CHECK），同一引擎复测：52 表、两遍幂等、8 条既有负向仍拒绝，另加 4 正 2 负（无状态字面量标识可写、两套 purpose 枚举互不放宽）全部符合预期；`server_version` / 扩展版本本轮当场读出。**未覆盖**：同上（性能与 `CREATE INDEX`）。

- **Alternatives**: 单独向量库（额外组件、双写一致性）；纯内存 ANN（无法持久与多副本）。

## R-02 驱动与向量编码（D-03）

## R-03 embedding 模型与维度（D-05）— **已冻结（2026-10-28）**

- **Decision（已冻结）**: 模型 **百炼 `text-embedding-v4`**，维度 **`vector(512)`**，cosine，写入前 L2 归一化；索引代际 1 = 精确扫描（不建 ANN）。
- **读数（2026-10-28 实测，`dev-env/evidence/d05-embedding-eval.json`）**: 语料 **156 文档 / 192 片段 / 70 查询**（60 可答 + 10 无答案），冻结规则见 `dev-env/evals/v2/SCORING_RULES.md`（SHA-256 `7ab7876b…`）。六候选维度全部被接口接受且实际返回维度与请求一致。**FullRecall@10**：512 = **1.0000**，768 = 0.9833，2048/1024/256 = 0.9667，1536 = 0.9500；**nDCG@10**：768 最高 0.9405，2048 0.9390，512 0.9344，1024 0.9328，256 0.9283，1536 0.9280；**MRR@10**：512 0.9151；**p95**：512 = 312 ms，最大 1536 = 391 ms（均 ≤ 500 ms）。按运行前冻结判据（FullRecall ≥ 0.90 / nDCG ≥ best−0.02 / p95 ≤ 500 ms），六者全部合格；按 (FullRecall, nDCG) 求 Pareto 前沿得 **{768, 512}**，两者 nDCG 差 **0.0061** 在 0.02 容差内视为并列，取更小维度 → **512**。用量 **162 请求 / 67 878 tokens / 0 重试**；**费用未测量**（未核实现行单价）。
- **作废的前一轮（v2）**: 首轮 172 文档 / 202 片段测得 FullRecall@10 0.9500 / nDCG@10 0.8568 并曾冻结 1536。独立复核发现该数据集三类事实错误（错误码标注指向不含该码的片段、同一属性跨文档多值、小时补零为 `010:00`），**结果作废**；v3 改为单一事实层重建并加生成期断言，**度量定义与选型阈值一字未改**。两版数据与结果分别保留在 `dev-env/evals/v2/{data-v2-archived,results-v2-archived}`。两轮 nDCG 差（0.8568 → 0.9344）本身即是"标注错误会压低度量"的证据。
- **分类别读数（512 维）**: 六类 `recall@10` 与 `full_recall@10` **全部 1.00**，`failures_512` 为空；`identifier` / `conflict` / `expired` 的 nDCG 与 MRR 均为 1.00，`cross_section` 0.9613 / 0.95，`table` 0.9631 / 0.95。**nDCG 的损失集中在 `zh_paraphrase`（0.6822，MRR 0.5906）**：12 个系统共用同一套属性措辞，改写查询常把正确片段排到第 2–5 名——**系统级区分必须靠元数据过滤，不能只靠向量相似度**。注意：v2 曾显示 `identifier` 类别失败，v3 修正标注后该类满分为 1.00，**故本实验不再支持"稠密向量对精确串天生不适用"的旧结论**；关键词路径（ADR-05）的保留理由回到设计需要（精确串、专名、罕见词与短查询），本轮未测其增益。

## R-04 索引与检索路径（D-06 / D-07）— **部分冻结**

- **索引代际 1（2026-10-28 冻结）**: **精确扫描，不建 ANN**。依据：D-05 语料仅 **192 片段**，该规模下 ANN 与精确扫描不可能产生可测差异，建 HNSW 无法验证召回损失。启用条件：片段数达到需要索引的规模后，按"召回 vs 精确基线 / 构建时间 / 索引体积 / 过滤后召回"实测，四项达标才启用。
- **关键词路径（设计需要，非 D-05 结论）**: 关键词路径用于精确串、专名、罕见词与短查询，并与向量路径做 RRF 融合；其增益**本轮未测**，保留理由是检索形态覆盖而非本实验读数（v2 曾据 `identifier` 失败声称"稠密向量不适用"，v3 修正标注后该类满分，该结论已撤回）。具体形态（`simple` / `pg_trgm` / 外部分词）仍按 ADR-05 待测，不提前冻结。
- **Decision（方法，保留）**: 先以精确扫描建立基线，再启用 HNSW；过滤条件导致召回不达标时不启用 ANN。中文关键词先走 `simple` + `pg_trgm`，外部分词扩展仅在不达标时评估。
- **实测（环境侧）**: HNSW 与迭代扫描在 0.8.7 可用（R-01）；但**本次未在 `vector(512)` 上实测 `CREATE INDEX`**，维度上限仍以官方说明为准，启用前必须实测。

## R-05 迁移事务与规模（D-27）— **已冻结（2026-11-01）**

- **Decision**: 迁移在前向事务内以 advisory lock 串行；逐级放大演练给出**本机、本夹具下的观察读数**，用于估算维护窗口与内存需求。**单事务 + 失败整体回滚是正确性要求**，B **不**做分段导入、**不**做断点续导；**不冻结任何"容量上限"数字**（理由见下文「这份读数能支撑什么、不能支撑什么」），超限只允许"扩大维护窗口 / 加内存 / 评估分区"，**不得**静默改成部分提交。
- **演练脚本**: `scripts/exp/migration_scale_drill.sh`（每级在**空 schema** 上完整跑 `db export → db verify --dump → db import → db verify --target`，结束 DROP 演练 schema；缺 `BASALT_TEST_PG_DSN` / `psql` 即失败、不跳过）。
- **环境（实测读数出处）**: PostgreSQL **17.11 (Debian 17.11-1.pgdg12+2)**，WSL2 内核 6.6.114.1，i7-12700 / 20 逻辑核 / **12 GiB 可用内存**，D: 盘 1.7 TB 可用。**单机单次读数，未做重复采样**——表中的时间与内存是"一次完整成功运行"的值，不是均值的置信区间。
- **计量口径（读表前先看这一段，每个数都指回具体探针）**:
  - **单位**：下表 **RSS 列是 KiB**（`/usr/bin/time -v` 的原生单位），**dump / WAL / 目标表列是字节**。换 GiB 一律按 `1024³ B` 计：百万级 RSS 4,165,116 KiB = 4,265,078,784 B = **3.97 GiB**；WAL 4,729,189,056 B = **4.40 GiB**（十进制 4.73 GB）。**别把「每消息 4.17 KiB」当成总量**——那是单条消息的读数，与上表的 KiB 总量不是同一层。
  - **导入 RSS**（`import_rss_kb`）= **导入那个 CLI 进程**的峰值 RSS，取自 `/usr/bin/time -v` 的 `Maximum resident set size (kbytes)`。**不是** PostgreSQL 服务端内存，也**不是**整机内存占用。成因：`readTableDump` 把整表 JSONL 一次性读进内存（不可流式回退），所以它随消息数线性增长。
  - **WAL 字节**（`wal_bytes`）= 导入单事务前后 `pg_current_wal_lsn()` 之差（`pg_wal_lsn_diff`），**是导入期间生成的全部 WAL 增量**，受 checkpoint 时机影响，不是稳态写入速率。
  - **WAL 峰值**（`wal_peak_bytes_per_s`）= **50 ms 采样**的每秒最大增量；采样线程自身也要连库，间隔有抖动，**不是瞬时真峰值**。
  - **目标表字节**（`target_total_bytes` / `messages_index_bytes`）= `pg_total_relation_size` / `pg_relation_size` 合计，**含索引与 TOAST**，不是堆表裸数据。
  - **dump 字节** = `db export` 产出的 JSONL 文件大小（未压缩）。
- **读数（四级同一脚本、同一口径）**:

  | 消息数 | dump 字节 | 导入 ms | 导入 RSS KiB | WAL 字节 | 目标表字节 | messages 索引字节 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 3,000 | 4,568,993 | 524 | 36,152 | 14,219,848 | 19,210,240 | 6,447,104 |
  | 30,000 | 40,989,195 | 3,553 | 142,080 | 127,924,176 | 73,752,576 | 19,529,728 |
  | 300,000 | 405,993,304 | 38,912 | 1,396,740 | 1,427,614,232 | 536,600,576 | 109,740,032 |
  | 1,000,000 | 1,352,705,836 | 197,626 | 4,165,116 | 4,729,189,056 | 1,721,729,024 | 336,175,104 |

  整窗（导入 + 校验）分别为 773 / 4,646 / 48,657 / 253,286 ms。**被测二进制不同**：前三级 `sha256=22ee87bcdf55…`（2026-11-01 本轮源码），百万级 `sha256=15e510c7b249…`（同日更早一次构建）——跨级的趋势可比，**不要**把两级读数的差值当成精确的时间差。夹具 `sha256`：前三级 `774af55f6f55…`，百万级 `87f50a9987dd…`。
- **每消息归一（趋势）**: dump ≈ **1.35 KiB/条**（1523 → 1366 → 1353 → 1353 B，30 万条后稳定）；导入 RSS ≈ **4.2–4.7 KiB/条**（12.05 → 4.74 → 4.66 → 4.17 KiB，30 万条后稳定）；WAL ≈ **3.5 × dump**（3.11 → 3.12 → 3.52 → 3.50）；目标表 ≈ **1.7 KiB/条**；导入吞吐在 30 万条后由 ~7,700 条/s 降到 ~5,100 条/s（`messages` 的 `tsv` 生成列与两个 GIN 索引 `idx_messages_tsv` / `idx_messages_content_trgm` 是主要成本）。**这些比值只对本夹具成立**——它用的是同一套合成消息内容与同一套索引，换数据或换索引配置，每消息字节与 RSS 都会变。
- **约束的先后次序（本机观察）**: **内存先于磁盘见顶**。导入 `readTableDump` 把整表 JSONL 读进内存，所以 RSS 随消息数线性增长且**不可流式回退**；WAL 是磁盘侧的次生约束（≈3.5 × dump，盘位充足时不构成首个限制）。这两者都**不是**同一种计量：RSS 是**客户端进程峰值**，`wal_bytes` 是**服务端 LSN 增量**，`wal_peak_bytes_per_s` 是 **50 ms 采样峰值**（百万级 119,097,210 B/s，30 万级 110,952,124 B/s），三者不可互相换算。
- **这份读数能支撑什么、不能支撑什么**:
  - **能支撑**：本机、本夹具上的**趋势与量级**——内存先见顶、WAL ≈ 3.5 × dump、30 万条后每消息成本趋于稳定；据此可以判断"这次迁移大概要留多久维护窗口、要多少内存"。
  - **不能支撑**：把它当成**普遍适用的容量保证**，也不要按上表线性外推成"4 GiB 内存就能导 93 万条"这类结论。每消息字节与 RSS 依赖**消息内容长度**、**`tsv` 生成列与两个 GIN 索引**、**并发导入**、**PG 参数**（`maintenance_work_mem` / `max_wal_size`）与 **Go 运行时行为**；换任一条件读数就会变。运维容量规划**必须**在目标机上用目标数据抽样重跑 `migration_scale_drill.sh`，本表只作对照基线。
- **超限或资源不足时的运维处置（三选一，**不得**改成部分提交）**:
  1. **耗时超维护窗口** → 扩大维护窗口（同机型同数据下百万级整窗 253 s 可作参照；导出与两次校验与导入同量级，别只算导入）；
  2. **WAL / 磁盘不足** → 先扩分区容量再跑；**不要**在导入中途切 `wal_level` 或清 WAL；
  3. **内存不足** → 加内存，或**评估分区 / 分批多事务**——后者是**产品与契约变更**（放弃"失败即空表"的单事务承诺），必须走模块评审与人工裁决，运维现场**不得**用循环调用 `db import` 绕过。

  超限失败是**安全失败**：进程 OOM 或任一校验失败都在单事务内整体回滚，目标 schema 保持空业务表——这正是"不静默部分提交"的落地形态。
- **未覆盖面**: 只有一种机型、一块磁盘、一个 PG 版本；未测并发导入争抢、未测目标库已有数据时的体积增长、未测 `maintenance_work_mem` / `max_wal_size` 调参后的差异；`wal_peak` 是采样值而非瞬时真峰值。

## R-06 事务未知结果与重试（C-13）

- **Decision**: 提交结果三态（成功 / 明确失败 / 未知）；未知时先 `VerifyTx` 按业务键复核，**只有确认不存在**才允许重试；`first_write_at IS NULL` 或普通 `SELECT` 查无行**不构成**未提交证据。
- **Rationale**: 网络中断与连接池回收会让提交结果不可判定，盲目重试会造成重复写入。
- **Alternatives**: 依赖数据库自增主键判重（无法覆盖业务键幂等）。

## R-07 advisory lock 与并发迁移

- **Decision**: 迁移在单个前向事务内执行 `pg_advisory_xact_lock(<固定键>)`，锁随事务释放；并发启动的第二个进程等待或超时失败，**不**在未见 schema 版本时抢先建表。
- **Rationale**: 多进程同时启动是新部署的常态。
- **读数**: 由 `TestPostgres_MigrateTakesAdvisoryLock` 覆盖（实施后）。

## R-08 时间、大整型与二进制映射

- **Decision**: 所有时间列 **`bigint` Unix 毫秒 UTC**（**不得** `timestamptz`——设计 C-13 / C-14 / §3.4.1，`MarkFirstWrite` 写 `at.UTC().UnixMilli()`，`TestPostgres_TimeColumnsAreUnixMillisUTC` 扫描列类型）；大整型用 `bigint` / `numeric` 明确映射；二进制用 `bytea`；SQLite 迁移时按列声明做无损转换并在校验阶段逐值比对。
- **Rationale**: SQLite 的动态类型会掩盖类型错误，迁移是唯一一次可见的校验机会。
