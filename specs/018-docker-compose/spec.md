# Feature Specification: Docker／Compose 单实例部署

**Feature Branch**: `018-docker-compose`

**Created**: 2026-11-02

**Status**: Draft（由已通过人工 review ① 的 US-18 R8 模块卡派生）

**Input**: 第18模块需求：Docker／Compose 部署——单实例镜像、持久化布局与容器验收。Basalt 已具备 PostgreSQL 唯一运行后端与 US-17 发布工具；企业需要一份能起、能看、能备份、能升级、能验收的 Linux/amd64 容器部署单元，而不是让每个部署者手工拼装。

## Clarifications

### Session 2026-11-02

- Q: 容器验收的枚举与跳过口径是什么？ → A: A1–A17 是唯一验收枚举；本地缺 Docker 或基础镜像时可跳过并登记未验证，**SKIP 不是通过**；CI 的 `container` job 缺依赖直接失败。（AI 依据 US-18 模块卡 §4.4 / §4.6 / §4.7）
- Q: 随附数据库与扩展能力检查的边界是什么？ → A: 随附 PostgreSQL 17 + pgvector 0.8.7，首启只由 initdb 脚本创建 `vector` 与 `pg_trgm`；应用启动检查 `vector`（≥ 0.8，`hnsw.iterative_scan`）与 `pg_trgm`，**不得**自行 `CREATE EXTENSION`；外部数据库由部署者预先创建扩展。（AI 依据模块卡 §2.4 / C-02）
- Q: 备份与恢复的执行身份与最小顺序是什么？ → A: 先停应用，再数据库转储、两个卷归档、secret 副本与校验清单；备份与恢复必须以 root 或一次性 root 容器执行，恢复后重设 secret 属主与权限；在线热备份不在本轮承诺。（AI 依据模块卡 §2.9 / C-11）
- Q: 镜像记录里 SBOM／provenance 的路径以哪里为基准？ → A: 以 image record 所在目录为基准；发布汇总复制进发布目录时保持文件名，再由校验和覆盖。（AI 依据模块卡 §2.10 / R7）
- Q: CI 清理的项目前缀与对象范围是什么？ → A: 容器、卷、网络、镜像统一按 `us18-ci-<run_id>-`（含尾随 `-`）匹配；先按真实项目名枚举 `down -v`，再按统一前缀清残留，最后断言四类对象零残留，有残留即 job 失败。（AI 依据模块卡 §2.10 / R8）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用官方镜像与 Compose 起一个可登录的单实例 (Priority: P1)

运维人员在 Linux 主机上准备好数据库口令与管理口令两个宿主文件，用官方 `linux/amd64` 镜像和随附 Compose 编排启动 Basalt；数据库扩展、迁移、健康检查、管理面登录都由部署单元完成，不需要自己拼装二进制或前端服务。

**Why this priority**: 这是容器交付存在的前提；起不来或登录不了，后续备份、升级、故障验收都无从谈起。

**Independent Test**: 在隔离项目名与临时端口上启动编排，从实例私有目录读出管理口令并登录管理台；整套过程可重复执行且不触碰用户正在运行的实例。

**Acceptance Scenarios**:

1. **Given** 已准备的镜像与两个宿主 secret 文件，**When** 运维执行启动，**Then** 数据库就绪、扩展能力检查、迁移与应用健康检查依次完成，管理面可登录。
2. **Given** 缺少镜像变量、任一入口限流变量或 secret 文件，**When** 运维执行配置或启动，**Then** 失败并点名缺失项，不静默取默认值。
3. **Given** 镜像与编排已就绪，**When** 检查镜像内容，**Then** 只有 Go 服务与内嵌管理台，无独立前端服务，无 Node／Python／MCP 运行期组件，启动过程不下载依赖。

---

### User Story 2 - 容器重建后实例身份、凭据与数据仍可用 (Priority: P1)

运维人员升级编排或重建应用容器（保留命名卷），实例标识、管理口令、知识原文、会话与运行记录都还在；旧管理口令仍可登录。

**Why this priority**: 容器重建是日常运维动作；若身份或凭据随容器层丢失，托管凭据将永久不可解密。

**Independent Test**: 记录实例标识并用旧口令登录 → 重建容器 → 实例标识不变、旧口令仍可登录、此前写入的知识仍可检索。

**Acceptance Scenarios**:

1. **Given** 已有实例与数据，**When** 仅重建应用容器且保留命名卷，**Then** 实例标识不变，旧管理口令有效，知识与会话数据仍在。
2. **Given** 实例私有目录被错误地放在工作区内，**When** 单独重建容器，**Then** 该错误布置必须被验收判红；私有目录必须在工作区之外的独立卷。
3. **Given** 删除命名卷，**When** 重新启动，**Then** 这是删除实例而不是重建；部署文档必须以显著警告写明。

---

### User Story 3 - 故障有可判定的行为（数据库、凭据、卷与停机） (Priority: P1)

运维人员遇到数据库不可用、错误数据库口令、工作区或 secret 权限错误、正常停机与强制终止时，能从日志与容器退出码判断发生了什么，且系统不会静默降级到本地存储或自动重跑未完成任务。

**Why this priority**: 目标客户要求可审计与可恢复；"看起来还能跑"比直接失败更危险。

**Independent Test**: 逐项制造故障，断言健康检查、业务请求、日志字面量、容器退出码与数据恢复终态；每项都有红态与恢复后的绿态。

**Acceptance Scenarios**:

1. **Given** 数据库停止，**When** 请求健康检查与业务端点，**Then** 健康检查仍为存活 200、业务端点 5xx、工作区内无本地数据库文件；数据库恢复后业务自行恢复。
2. **Given** 错误数据库口令，**When** 启动应用，**Then** 应用非零退出，日志点名连接失败但不回显口令。
3. **Given** 工作区不可写或 secret 属主／权限不符，**When** 启动，**Then** 应用非零退出并点名路径／`Permission denied`；按文档修正属主后可以启动，且权限不得放宽为世界可读。
4. **Given** 应用正在处理会话运行，**When** 收到 `SIGTERM`，**Then** 在既有 70 秒宽限内按自身结果收尾并以 0 退出；宽限到期分支由既有组件测试覆盖，编排层 90 秒强杀是外部兜底而不是正常退出。
5. **Given** 应用被 `SIGKILL`，**When** 重新启动，**Then** 数据保留，`running` 运行收口为失败、半截工具组收口为未知，**不**自动重跑外部动作。
6. **Given** 同一工作区与数据库启动第二个应用容器，**When** 第二实例启动，**Then** 因工作区实例锁退出非零并点名锁。

---

### User Story 4 - 四件套备份与全新项目恢复 (Priority: P1)

运维人员停机后做数据库、工作区、实例私有目录与宿主 secret 的配套备份，并在全新项目名上恢复；旧管理口令、旧托管连接、知识原文与检索结果都可用，恢复后 secret 属主与权限符合规定。

**Why this priority**: 只备份工作区会丢主密钥与管理口令，恢复后托管凭据不可解密；这是最容易发生的"备份看似成功、恢复不可用"。

**Independent Test**: 备份 → 删除或改用全新项目 → 恢复 → 旧口令登录、旧知识命中、实例标识一致、两个 secret 的属主与权限读数正确。

**Acceptance Scenarios**:

1. **Given** 运行中的实例，**When** 执行配套备份，**Then** 输出数据库转储、两个卷归档、两个 secret 副本与校验清单，备份目录仅所有者可访问。
2. **Given** 备份产物，**When** 恢复到全新项目，**Then** 旧管理口令与旧托管凭据可用，知识检索结果一致，secret 属主／权限被重设。
3. **Given** 只恢复工作区而遗漏实例私有目录，**When** 执行验收对照，**Then** 恢复用例必须判红。

---

### User Story 5 - 镜像升级与受控回退 (Priority: P2)

运维人员在停止应用、完成升级前备份后切换镜像 digest，启动时执行既有前向迁移；回退只允许"恢复升级前备份 + 回到旧镜像"，不支持裸镜像降级。

**Why this priority**: 升级路径必须与备份绑定；没有回退承诺的升级会把数据置于不可逆风险。

**Independent Test**: 镜像 A 写数据 → 备份 → 换镜像 B → 数据与凭据可用 → 在新项目用备份与镜像 A 恢复 → 数据可查，secret 权限正确。

**Acceptance Scenarios**:

1. **Given** 已有实例与升级前备份，**When** 切换到新镜像并启动，**Then** 既有数据、实例标识与旧口令可用，迁移在启动时完成。
2. **Given** 升级后的状态，**When** 执行回退，**Then** 只能恢复升级前备份并回到旧镜像；裸镜像降级必须被文档与验收排除。
3. **Given** 只有一个可用版本，**When** 评估跨 schema 回退，**Then** 该项登记为未验证，不得写成已通过。

---

### User Story 6 - 镜像进入发布记录与校验链 (Priority: P2)

发布负责人生成镜像记录（本地镜像标识、二进制哈希、基础镜像 digest、模板哈希、SBOM、provenance、扫描状态），把它交给既有发布汇总；矩阵按平台与类别分行，校验工具能逐项核对，正式记录可要求仓库 digest。

**Why this priority**: 镜像必须能证明"测的是哪个镜像"；否则容器验收与发布记录脱钩。

**Independent Test**: 镜像记录 → 发布汇总 → 校验贯通；篡改 SBOM、删除镜像列表但保留矩阵镜像行、或矩阵与镜像记录任一方出现孤儿行时必须失败。

**Acceptance Scenarios**:

1. **Given** 合法镜像记录与 SBOM／provenance 文件，**When** 执行发布汇总，**Then** 镜像字段写入发布记录与清单，文件进入校验和与签名覆盖范围，矩阵出现 `image` 行。
2. **Given** 矩阵含镜像行但发布记录无镜像列表（或反向），**When** 执行校验，**Then** 失败并点名不一致。
3. **Given** 正式发布要求仓库 digest，**When** 镜像记录的仓库 digest 为空或格式非法，**Then** 校验失败；无镜像记录的旧发布目录不因该要求失败。
4. **Given** 构建上下文混入私钥文件或含私钥内容的文件，**When** 构建镜像，**Then** 在调用容器构建前拒绝并点名文件。

---

### Edge Cases

- 镜像平台不是 `linux/amd64`，或二进制不是 `CGO_ENABLED=0`。
- 基础镜像或数据库镜像 digest 与锁文件不一致。
- 宿主 secret 文件位于 9p／drvfs（WSL `/mnt/d`）等忽略属主与权限的文件系统。
- 数据库扩展缺失或版本能力不足；数据库 schema 版本高于当前二进制。
- 健康检查在数据库断开后仍为 200，被误读为"数据库就绪"。
- 手动补跑（300 秒预算）在停机时越过 70 秒宽限。
- 备份只覆盖工作区，遗漏实例私有目录或 secret。
- 同一平台同时存在归档行与镜像行，按 `(平台, 架构)` 匹配会撞键。
- 无 Docker 守护进程或基础镜像未缓存；CI 干净 runner 没有本地缓存。
- 测试清理按精确项目名执行，漏掉按项目派生的卷、网络与镜像。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 交付 MUST 提供官方 `linux/amd64` 的 `binary` 档应用镜像，内容为 Go 服务、内嵌管理台、基础镜像件与许可证；**不得**另起前端服务。
- **FR-002**: 镜像 MUST **不**包含 Node、Python、内置 MCP 组件或发布签名私钥；缺失组件 MUST 在启动日志点名且**不得**下载；文档**不得**宣称 `full` 档或"完整 MCP 支持"。
- **FR-003**: 所有运行期依赖 MUST 在构建阶段准备；正常启动**不得**下载任何包管理器依赖。
- **FR-004**: 交付 MUST 提供 Compose 编排，包含应用与 PostgreSQL/pgvector 两个服务、数据库卷、工作区卷、实例私有卷与两个宿主 secret；单副本、非 root、只读根文件系统、丢弃全部 capability、禁止提权、健康检查与 90 秒停机宽限。
- **FR-005**: 配置模板 MUST 从 secret 文件解析数据库连接串，**不得**把 DSN 或口令写入镜像、配置模板或发布记录；六项入口限流 MUST 显式提供，缺任一项在编排配置阶段失败。
- **FR-006**: 首启 MUST 从镜像模板播种工作区配置且此后不覆盖；实例私有目录 MUST 位于工作区之外的独立卷，保存主密钥与管理口令。
- **FR-007**: 启动 MUST 依次完成数据库就绪、扩展能力检查、受控前向迁移与应用健康检查；扩展检查 MUST 覆盖 `vector`（≥ 0.8，`hnsw.iterative_scan`）与 `pg_trgm`，应用**不得**自行创建扩展；任一步失败 MUST 非零退出并点名原因，**不得**回退 SQLite 或本地文件。
- **FR-008**: 健康检查 MUST 只表示进程存活；**不得**被文档或验收表述为数据库就绪或业务可用。
- **FR-009**: 应用 MUST 以非 root 用户运行；容器可写位置 MUST 仅限工作区卷、实例私有卷与临时文件系统。
- **FR-010**: `SIGTERM` MUST 触发有序停机：先停止接收新请求，再在既有 70 秒宽限内等待在途 HTTP 按自身结果收尾；宽限到期 MUST 返回错误并非零退出；调度器在途任务 MUST 由独立宽限收口。
- **FR-011**: 重启后的数据保留与未完成任务恢复 MUST 分开表述；恢复 MUST 沿用既有契约（未完成运行收口为失败、半截工具组收口为未知），**不得**新增隐式自动重跑。
- **FR-012**: 工作区实例锁 MUST 拒绝第二应用容器；交付**不得**暴露多副本、扩缩容、Kubernetes、Swarm 或滚动升级入口。
- **FR-013**: 交付 MUST 提供数据库、工作区、实例私有目录与宿主 secret 的配套备份、校验清单与恢复到全新项目的脚本；备份 MUST 先停应用再转储与归档，且以 root 或一次性 root 容器执行；**不得**只备份工作区，**不得**把在线热备份作为本轮承诺。
- **FR-014**: 恢复 MUST 重设两个 secret 的属主与权限（数据库口令 `root:root 0400`、应用 DSN `10001:10001 0400`），**不得**以世界可读绕过。
- **FR-015**: 升级 MUST 先停应用并完成升级前备份，再切换镜像 digest；回退 MUST 只支持"恢复升级前备份 + 旧镜像"，**不得**支持裸镜像降级；本轮**不得**新增自动升级平台。
- **FR-016**: 镜像记录 MUST 绑定镜像标识、二进制哈希、基础镜像 digest、Dockerfile／入口脚本／配置模板哈希、SBOM 与 provenance 哈希；SBOM 与 provenance 路径 MUST 相对记录所在目录，复制进发布目录时保持文件名。
- **FR-017**: 镜像记录 MUST 能进入既有发布汇总，写入发布记录与清单，并纳入校验和与签名覆盖范围；支持矩阵 MUST 按 `(操作系统, 架构, 类别)` 区分归档行与镜像行。
- **FR-018**: 校验工具 MUST 在矩阵含镜像行或发布记录含镜像列表时逐项核对，并强制两者一一对应；可选要求仓库 digest 非空且格式合法；无镜像的旧发布目录 MUST 仍然合法。
- **FR-019**: 镜像构建 MUST 在调用容器构建前拒绝私钥文件名、secret／私有路径或含私钥内容的文件；**不得**读取发布签名私钥。
- **FR-020**: 容器验收 MUST 使用真实镜像与真实 Compose，按 A1–A17 唯一枚举覆盖管理面登录、一次任务、知识检索、容器重建、备份恢复、数据库不可用、错误凭据、卷权限、secret 权限、优雅停机、崩溃不重跑、第二实例拒绝、升级回退与清理隔离；本地缺依赖可跳过并登记未验证，**SKIP 不得计为通过**。
- **FR-021**: 验收环境 MUST 使用独立项目名、独立卷与随机宿主端口；清理 MUST 覆盖容器、卷、网络与镜像并断言无残留，**不得**触碰用户实例。
- **FR-022**: 部署 CI MUST 在 Linux 宿主匿名拉取固定 digest 的公开基础镜像，运行容器验收，上传运行报告，并按 `us18-ci-<run_id>-` 统一前缀清理容器、卷、网络与镜像后断言无残留；**不得**登录或推送镜像仓库，缺依赖**不得**以跳过代替失败。
- **FR-023**: 运维文档 MUST 给出镜像构建、secret 准备、启动、登录、备份、恢复、升级、回退与停机的可复制命令，并写明 9p／drvfs 限制与"删除卷即删除实例"的警告。

### Key Entities

- **应用镜像**：`binary` 档、`linux/amd64` 的单二进制镜像，含服务与内嵌管理台，不含运行时组件与私钥。
- **部署单元**：Compose 编排、应用镜像、数据库镜像、数据库卷、工作区卷、实例私有卷与两个宿主 secret。
- **工作区**：容器内配置、实例名册、实例锁、Agent 定义与知识原文的持久位置。
- **实例私有目录**：工作区之外的主密钥与管理口令存放位置，按实例标识命名。
- **镜像记录**：镜像标识、版本、平台、档位、二进制与模板哈希、基础镜像 digest、SBOM／provenance 哈希、扫描状态与证据。
- **发布记录与支持矩阵**：既有发布工件，新增可选镜像列表与按类别区分的矩阵行。
- **备份集**：数据库转储、工作区归档、实例私有目录归档、宿主 secret 副本与校验清单。
- **容器验收证据**：断言、原始输出、容器退出码、日志字面量与清理残留读数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在干净 Linux 主机上，按文档准备 secret 并执行启动后，管理台在 60 秒内可登录；失败时日志点名具体缺失项或失败阶段。
- **SC-002**: 100% 的容器重建保留卷场景中，实例标识、管理口令与已有知识数据可用；失败率为 0。
- **SC-003**: 数据库不可用场景中，健康检查保持存活 200、业务端点返回 5xx、工作区无本地数据库文件；数据库恢复后业务无需重启应用即恢复。
- **SC-004**: 正常停机时，空闲与会话运行场景的容器退出码为 0 且不超过 90 秒；强制终止后重启，未完成运行 100% 收口为失败、半截工具组 100% 收口为未知，外部动作新增调用为 0。
- **SC-005**: 配套备份恢复后，旧管理口令登录成功率 100%，旧知识检索命中 100%，两个 secret 的属主与权限 100% 符合规定且其他用户不可读。
- **SC-006**: 镜像记录经发布汇总后，校验工具对篡改 SBOM、镜像列表与矩阵孤儿行的检出率为 100%；合法记录 100% 通过。
- **SC-007**: 全部容器验收结束后，按项目前缀检查的四类对象残留数为 0，且未对用户实例执行任何命令。
- **SC-008**: 部署 CI 在无本地缓存的干净 runner 上完成容器验收，运行报告 100% 上传；缺 Docker 或缺失基础镜像时判失败而不是跳过。

## Assumptions

- 运行期存储已是 PostgreSQL（含 pgvector 与 `pg_trgm`），本 US 不引入第二条存储路径；单实例结论仍成立，理由是会话锁、工作区实例锁与调度／恢复归属。
- 复用 US-17 的发布工具、记录格式、校验工具、SBOM 与 provenance 框架；镜像面是 US-18 的新增代码面，不写成 US-17 既有能力。
- 容器平台只承诺 `linux/amd64` 与 Docker Compose v2；其他架构、Docker Desktop、podman、rootless Docker、Kubernetes、Swarm 不在本轮。
- 随附 PostgreSQL 17 + pgvector 0.8.7 参与全部用例；外部 PostgreSQL 只给 override 口径，不实测。
- 本机 Docker 只在 WSL Ubuntu；Windows 验收经 WSL 包装，secret 目录必须位于 Linux 原生文件系统或 Docker 卷。
- 容器验收使用 mock 模型；真实模型、外部通知、镜像仓库推送、漏洞扫描与正式签名不在本轮授权内。
- 首次正式发布仍在 US-25 验收之后，由用户给出版本并触发；US-18 只产出可本地验证的镜像与记录。
- 本 US 不新增产品配置键、数据库表、HTTP 端点或契约字面量。
