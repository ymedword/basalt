# Feature Specification: 制品与版本发布

**Feature Branch**: `017-release-artifacts`

**Created**: 2026-11-02

**Status**: Approved for implementation (human review ①, 2026-11-02); 2026-11-02 用户同意缩减收口范围，延期项见文末「范围调整」

**Input**: 为 Basalt 自托管部署提供可下载、可校验、可升级、可回滚的发布物；覆盖四平台归档、full/binary 两档、确定性打包、SHA256SUMS + Ed25519 签名、SBOM、发布记录、仅下载目录校验、单机升级/失败恢复与私有资产快照。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 下载并校验发布物 (Priority: P1)

运维人员从发布页下载一个平台的归档、哈希清单、签名和校验工具，在没有源码、没有 Go 工具链的目标机器上验证归档完整性与签名，然后解压启动。

**Why this priority**: 没有可验证的下载物，企业私有部署无法建立信任链。

**Independent Test**: 在只读下载目录、最小 PATH 环境运行校验工具；篡改归档或缺签名时必须拒绝。

**Acceptance Scenarios**:

1. **Given** 完整发布目录与带外公钥，**When** 运维执行校验，**Then** 归档、清单、记录签名全部通过，退出码为 0。
2. **Given** 归档被篡改或缺少签名，**When** 运维执行校验，**Then** 校验失败并点名字段，不降级为只校验哈希。
3. **Given** 无源码、无 Go 工具链的目录，**When** 运维执行发布目录自带的校验工具，**Then** 校验可完成。

---

### User Story 2 - 构建四平台发布物 (Priority: P1)

发布负责人从干净工作区构建 Windows/amd64、Linux/amd64、Linux/arm64、macOS/arm64 四个归档，生成清单、SBOM、发布记录与支持矩阵。

**Why this priority**: 四平台归档是本 US 的核心交付；缺平台或档位内容错误会让部署直接失败。

**Independent Test**: 四个归档存在且可解压；full 含运行时组件，binary 不含；两次构建哈希一致。

**Acceptance Scenarios**:

1. **Given** 已批准的版本号与 tag，**When** 发布负责人执行构建，**Then** 四个归档与各自清单生成，版本、提交号、目标平台一致。
2. **Given** 相同输入，**When** 连续构建两次，**Then** 归档 SHA-256 相同。
3. **Given** 包内出现私有路径或真实凭据，**When** 执行打包，**Then** 打包失败且不产出归档。

---

### User Story 3 - 单机升级与失败恢复 (Priority: P1)

运维人员在单机上从旧版本升级到新版本；升级失败时用备份恢复旧版本，旧数据仍可读。

**Why this priority**: 发布物不能只有构建，必须有可执行、可回退的升级路径。

**Independent Test**: 在旧版本写入数据并备份，制造备份后的可识别变化，再升级失败并恢复；变化必须消失，旧版必须可启动。

**Acceptance Scenarios**:

1. **Given** 旧版本实例与旧数据，**When** 升级成功，**Then** 数据迁移到当前 schema，旧会话/任务可读，新任务可运行。
2. **Given** 升级失败，**When** 执行恢复，**Then** 三对象备份与旧二进制恢复，备份后写入不残留。
3. **Given** 恢复步骤被省略，**When** 运行对照测试，**Then** 测试必须失败，证明恢复用例有判别力。

---

### User Story 4 - 私有资产快照 (Priority: P2)

维护者把不入库的私有配置、凭据引用和本地材料做成带清单的快照，并在新工作区恢复。

**Why this priority**: 私有资产不能靠发布 tag 备份；错误删除会导致不可恢复的本地状态丢失。

**Independent Test**: 快照、删除源、恢复；逐文件哈希一致，清单包含排除规则本身。

**Acceptance Scenarios**:

1. **Given** 私有文件集合，**When** 创建快照，**Then** 输出在 worktree 之外，清单只含相对路径。
2. **Given** 快照归档，**When** 恢复到空目录，**Then** 逐文件哈希一致。
3. **Given** 归档含越界路径或符号链接逃逸，**When** 恢复，**Then** 拒绝。

---

### Edge Cases

- tag 存在但不指向 HEAD；工作区脏；版本号带 `v` 前缀。
- 四平台中某个归档缺失，或 full 档缺少运行时组件。
- 签名密钥缺失、公钥不匹配、`SHA256SUMS.sig` 缺失或被篡改。
- 包内包含 `.env` 普通文本（不得误判）与 PEM 私钥（必须拒绝）。
- 归档两次构建哈希不同。
- 升级时数据库 schema 已是当前版本，无法证明迁移。
- 备份后、恢复前产生新数据；只换回旧二进制而不恢复数据。
- 私有快照归档含绝对路径、`..` 路径或符号链接逃逸。
- Linux/arm64 没有真机，不能静默写成已运行。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 生成 Windows/amd64、Linux/amd64、Linux/arm64、macOS/arm64 四个平台归档，命名包含版本、平台与架构。
- **FR-002**: 系统 MUST 区分 full 与 binary 两档；full 含运行时组件，binary 不含，且两档内容与运行时清单一致。
- **FR-003**: 相同输入重复构建 MUST 产生相同归档哈希。
- **FR-004**: 系统 MUST 拒绝包含私有路径、真实凭据或私钥的归档；普通 `.env` 文本不得被误判。
- **FR-005**: 版本号、tag、提交号、二进制自报版本、归档名与发布记录 MUST 一致。
- **FR-006**: 系统 MUST 生成覆盖发布文件的 `SHA256SUMS`，并按“记录 → 记录签名 → 校验和 → 校验和签名”的顺序签名。
- **FR-007**: 正式发布 MUST 使用 Ed25519 签名；无签名只允许标记为预演，且不得作为发布物上传。
- **FR-008**: 系统 MUST 生成包含 Go 模块、内嵌前端与运行时组件的 SBOM，并如实标记缺口。
- **FR-009**: 系统 MUST 生成发布记录、发布说明与支持矩阵；记录不得含绝对路径、凭据或私有文档内容。
- **FR-010**: 运维人员 MUST 能在没有源码和 Go 工具链的下载目录中校验归档与签名。
- **FR-011**: 每个平台的归档 MUST 在匹配宿主上解压、启动、通过健康检查并执行 mock 任务；Linux/arm64 无真机时不得静默降级。
- **FR-012**: 系统 MUST 支持单机升级，保留旧数据并迁移到当前 schema。
- **FR-013**: 升级失败 MUST 能用 PostgreSQL dump、workspace、配置/密钥三对象备份与旧二进制恢复；恢复测试必须包含备份后的可识别变化。
- **FR-014**: 系统 MUST 支持私有资产快照与恢复，输出在 worktree 之外，并拒绝越界路径。
- **FR-015**: 发布 CI MUST 只构建与上传，不创建 tag、不 push、不创建 GitHub Release。

### Key Entities

- **归档**：一个平台与档位的发布文件，含程序、可选运行时组件、许可证与包内清单。
- **发布目录**：归档、校验和、签名、SBOM、发布记录、说明与支持矩阵的集合。
- **宿主证据**：某平台实际启动与冒烟检查的结果，区分已运行、仅编译、未测试。
- **发布记录**：版本、提交、工具链、归档哈希、签名状态、证据与限制。
- **升级备份**：PostgreSQL dump、workspace 与配置/密钥三对象，带时间与哈希。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 四个平台归档全部生成，且都能解压并通过静态内容校验。
- **SC-002**: 同一输入连续两次构建的归档 SHA-256 完全一致。
- **SC-003**: 完整发布目录在最小 PATH 环境中校验通过；任一篡改、缺签名或缺文件都会失败。
- **SC-004**: 两个 full 平台在匹配宿主上完成启动、健康检查与 mock 任务；Linux/arm64 的实际结果被如实记录。
- **SC-005**: 升级成功后旧数据可读、新任务可运行；升级失败后恢复可让备份后的变化消失。
- **SC-006**: 私有快照恢复后逐文件哈希一致，越界路径被拒绝。
- **SC-007**: 发布 CI 中不存在创建 tag、push 或创建 Release 的步骤。

## Assumptions

- 生产签名密钥由用户保管；测试只使用临时密钥。
- 运行期存储为 PostgreSQL，升级备份包含数据库 dump 与 workspace。
- 当前没有 Linux/arm64 真机；该项按未验证登记，需用户提供机器或书面裁决延期。
- GitHub Release、tag 与对外发布由用户执行，本 US 不自动执行。
- 不新增第三方依赖；发布工具使用 Go 标准库。
- 容器镜像归 US-18，故障演练归 US-31，均不在本 US 范围。

## 2026-11-02 范围调整（用户明确同意）

US-17 按「发布基础工具」收口，首个正式版本安排在 US-25 完成验收之后，由用户给出版本并触发。本次**不**冒充通过、延期到首次正式发布前的验收项：

- FR-007 正式签名与仅下载目录的独立验证（需正式密钥与发布目录；密钥授权已记录，尚未触发发布）。
- FR-011 / SC-001 / SC-004 中四平台真实宿主证据与真实 full 制品：本机只有 windows/amd64，`release/runtime/` 组件不齐，full 档现按 `release/runtime-manifest.json` 硬门禁拒绝出包。
- FR-012 / FR-013 / SC-005 单机升级与失败恢复的真实环境实测：工具已实现，闭环未验证；`releasekit upgrade` 在 CLI 与 `docs/Operations.md` 中标为受限入口，生产升级按人工步骤执行。
- SC-003 / SC-007 的发布工作流真实运行：仅在手动触发且组件备齐后才产出正式候选。

本次收口实际验证：source 层单元 / 竞态 / 签名顺序 / 打包安全 / SBOM / 记录 / stage 映射、`make check`、候选形态 e2e、私有快照往返。未验证项逐条登记在 `run-state.md` §4（U1–U7）与 §7。
